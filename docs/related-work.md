# 同類專案的可借鏡之處(離線字幕 → 即時聽譯)

> **這份文件的性質:2026-08 的一次生態掃描,不是實驗結果。**
> 關於**別人的產品**的敘述來自其官網、README 與作者說法,**本專案沒有複驗過**;
> 引用到 **kikemu 自己的數字**時一律附出處,並已與 `results/` 對過
> (對不上的地方直接改掉,見文末「與 `results/` 對帳」)。
>
> 掃描對象:What'Sub(壹加壹,商用)、KIAO Voice(商用)、VidScribe、
> QwenASRMiniTool、M2L3、Scribe Studio、SubtitleAI、Outtake。

**注意:這些幾乎全是離線批次工具。** 每一節都分成「他們怎麼做」與
「即時場景怎麼改」——後者才是 kikemu 要的,而且往往結論相反。

---

## 0. 最重要的一條:管線不是資產

四個開源專案在幾個月內出現,做的事高度重疊,且都能週末組完。
**能自己組,代表管線沒有護城河。**

不能複製的只有兩樣:

1. **累積的人工校正資料**(壹加壹的多年字幕)
2. **使用者願不願意把校對時間交給你**

**對 kikemu 的意涵:別在管線上找差異化。** 差異化在詞表怎麼累積、以及誰在複核。

---

## 1. 四階段拆分(M2L3)

M2L3 把管線寫成四個獨立階段,各用不同模型:

| 階段 | 用什麼 |
|---|---|
| ASR | WhisperX (faster-whisper-large-v3) + Silero VAD |
| **Alignment** | **Wav2Vec2 音素級 forced alignment** |
| Segment(斷句) | 本地 LLM 或線上 API |
| Translate | 本地 LLM 或線上 API |

**值得學的是「斷句」被獨立成一個階段。** 我們一直把斷句當成 ASR 或翻譯的
附帶產物,但它其實是獨立問題——它決定閱讀節奏,而閱讀節奏決定體感品質。

### → 即時版怎麼改

即時沒有「全文都在手上」這個前提,所以斷句從**回顧式**變成**預測式**:

- 離線:看完整段再決定在哪斷 → 最佳斷點
- 即時:**只能靠已定稿的部分 + VAD 停頓**決定斷點,而且一旦顯示就不能反悔

務實做法:**用 VAD 的停頓當主要斷點來源,LLM 只在停頓不明顯時介入**
(長句連說)。這樣多數情況零延遲,少數情況才付一次呼叫。

翻譯階段同理:**只翻定稿段落**,暫定段落不送翻譯(見 §6)。

---

## 2. Forced alignment 是獨立的一層

多個專案把「產文字」與「定時間」拆成兩個模型:

- M2L3:Wav2Vec2 音素級對齊
- QwenASRMiniTool:`qwen3-forced-aligner-0.6b-GGUF`(0.6B,GGUF)

QwenASRMiniTool 的作者宣稱因此「1 小時以上長影片字幕基本不會飄移」——
**正是 ytplayer 標在已知未解的那一項**(時間戳由模型從 token 位置估算)。

兩者取捨:Wav2Vec2 是聲學模型直接對齊音素,比另一個生成模型猜可靠;
Qwen aligner 較輕、格式現成。

### → 即時版怎麼改

**即時不需要 forced alignment,而且做不了**——FA 要先有完整音訊與完整文字。

即時的時間戳直接來自串流 ASR 的詞級輸出(SM 有、Deepgram 有)。
**這反而是選專用 ASR 而非一體式模型的又一個理由**——與報告 §3.4 的結論一致:
要詞級 timestamp,LLM 那條路直接出局。

FA 的用武之地在 kikemu 的**事後成品那一趟**:結束後拿完整錄音重跑,
產出精確對齊的雙語逐字稿。那一趟本來就是離線的,可以直接套用上面的做法。

## 3. 詞表回流迴路(Scribe Studio)

```
確定性詞表替換(種子 40+ 條 + 個人累積)
  ↓
LLM 校對
  ↓
使用者 accept → 回流進個人詞表
```

**關鍵是最後一步:使用者接受的修正自動變成詞表條目。**
What'Sub 也有類似設計(「改過的字會記住」)。

這比手動維護詞表強在:零額外操作、且累積的是**真實發生過的錯誤**,
不是想像中的。

### → 即時版怎麼改

**即時場景的死穴:Speechmatics 的詞表是 session config,連線後無法更新。**
中途學到的詞這一場用不上。(這條已寫在 `stt-matrix.md` 的踩雷筆記。)

所以迴流的單位要往後挪一格:

- 這一場學到的詞 → **回填到該地點/該客戶的詞表**
- 下一個使用者、下一場才受惠

這跟 kikemu 已驗證的「以地點為 key 的詞表」是同一個機制,只是補上了
「哪裡來的新詞」這一半。**複核者做的每一個選擇就是標註。**

> 這一條與 §8 的「並排雙跑 + 人工複核」是同一套流程的兩半:
> 複核產生選擇,選擇回流成詞表。報告 §8 量過複核負擔約 11% 全文。

若真要場內更新:只能在自然間隙(講者移動、使用者按暫停)重連一次,
把斷口藏在沒人在聽的時間裡。排 v2。

## 4. 前端抽音訊(What'Sub)

官網明講:影片全程留在使用者電腦,只擷取聲音上傳。
前端用 WebCodecs 或 ffmpeg.wasm demux。

**效益:**一小時 1080p 影片約 2 GB → 16k 單聲道 → Opus 約 15 MB,
**上傳量差約 130 倍**。

**實作要點:**

- 走 WebCodecs(硬體加速),失敗才退回 ffmpeg.wasm(格式通吃但慢)
- **記憶體是主要限制,不是 CPU**。必須串流式分塊,不要整包載入
- 跑在 Web Worker 裡

### → 即時版怎麼改

即時本來就是逐塊上傳,不存在「先抽再傳」的問題。但同一個原則適用:
**在裝置端就轉成 16k 單聲道 PCM/Opus 再上行**,而不是傳原始取樣率的音訊。
manemu 的 AudioWorklet 已經是這個做法,kikemu 直接沿用。

事後那一趟若要上傳完整錄音,前端 demux 就用得上。
⚠️ 但要先確認與 PRD §2「內容零留存」的界線怎麼畫——
目前伺服器不存音訊,事後那一趟要嘛在裝置端做完,要嘛改規格。

## 5. 兩個具體的坑

### 5.1 依語言決定要不要 OpenCC

QwenASRMiniTool 修過一個 bug:**語言選日文時要跳過 OpenCC 繁化**,
否則「会・静・図」會被誤轉成「會・靜・圖」。

**kikemu 有同樣風險:**日文原文欄位、事後產出的雙語對照、
任何保留來源語的地方,全域套 `s2twp` 都會踩到。

**規則:OpenCC 依「該欄位的語言」決定套不套,不要全域套用。**

這種錯誤在只看中文譯文時察覺不到,是上線半年才會有人回報的那種。

> 本專案的評測腳本已經是依語言決定的(`exp5/scripts/score_zh.py` 只在中文計分時
> 折疊簡繁),**但 app 端沒有逐欄位檢查過**——這是 §8 排第一的原因。

### 5.2 辨識提示(initial_prompt)是可用的旋鈕

QwenASRMiniTool 把「辨識提示/參考文字」做成主要功能
(可貼歌詞、關鍵字、背景說明)。VidScribe 沒開放。

對 Whisper 系模型,這是**唯一在解碼當下生效**的偏置手段——
軟提示、不可靠,但成本為零。

### → 即時版

專用 ASR 有正式的 keyterm/custom dictionary,不需要靠 initial_prompt。
**這一條只在 Whisper 系(Breeze 本機分支)才用得上。**

> 對得上我們量到的一條侷限:**Breeze 沒有詞表機制**(`stt-matrix.md` §6 侷限 3)。
> initial_prompt 是它唯一可用的替代手段,而且**本專案沒測過**。

## 6. 即時獨有:離線工具完全沒有的問題

以下沒有任何一個參考專案處理過,因為它們都是批次的。

### 6.1 兩層時間軸(暫定 / 定稿)

串流 ASR 會回頭改前文。直接顯示會讓字幕不斷跳動,讀十分鐘就累。

做法:**只 commit 超過 N 秒的內容為定稿(實色),之前的維持暫定(淡色)**。
暫定文字被改寫不算跳動。

kikemu 實測(報告 §4,exp1 arm C / C+):
**partial p50 0.37s / 0.35s、final p50 2.27s / 2.24s**(`max_delay=2.0`)、
**改寫率 0.16 / 0.17**。詞表對延遲與改寫率**零影響**。

**顯示策略:暫定階段不顯示譯文**(或只顯示節奏指示),定稿後才出中文。
避免「先看到日文再被替換成中文」的跳動。

### 6.2 滾動緩衝(補回錯過的開頭)

對話式場景(餐廳、突發問答)使用者來不及按錄音。

做法:**背景持續保留最近 10 秒音訊但不上傳**,按下按鈕時連同那 10 秒一起送出。
避免一直監聽的誤觸發與成本。

> 已寫進 `stt-matrix.md` 的情境矩陣(「餐廳短互動」那一列)。

### 6.3 長場次的 session 輪替

串流連線會有延遲漂移,約每 45~50 分鐘要無縫換 session。
Chirp 3 更嚴格,串流上限 5 分鐘、需 stream rotation。

**必須一開始就設計進去,不能事後補。**

### 6.4 分歧率當音質護欄

kikemu 的並排雙跑實驗(報告 §8 / `analysis/dual_run.py`)量到:
**實質分歧率**隨音質單調上升(N0 乾淨 **8.6%** → N2 15.1% → N3 人群 8dB **47.5%**),
而分歧處的勝率同步從 **0.78** 滑向 **0.45**。

**分歧率是不需要額外量測的音質代理指標。** 可作為執行期規則:

```
實質分歧率 > 25% → 回報「錄音品質不足,請檢查拾音」
```

⚠️ **一定要用「實質」分歧率,不是全分歧率**(全分歧率是 11.0% → 49.0%,
含大量標點與形式差異)。用全分歧率會在自發語音上誤擋——
`stt-matrix.md` §8 已經記過這條。門檻 25% 是依五個條件粗估,**需以實際語料校準**。

### 6.5 即時 vs 事後 的價值重心

離線工具的產出物就是字幕檔。kikemu 不是——

- **即時那一趟:只要「跟得上、看個大概」**,不必跟任何人比品質
- **事後那一趟才是產品**:高品質逐字稿、翻譯、術語表、譯註、摘要

這讓你不必在即時品質上跟 Google/Apple 的免費功能競爭。

**事後那一趟的成本(實測牌價,`stt-matrix.md` 成本速查):**

| 路線 | 每小時音訊 |
|---|---|
| Gemini `generateContent`(聽)+ Gemma 4 26B(譯) | **≈ $0.265** |
| Speechmatics 批次(要詞級時間戳)+ Gemma 4 26B | ≈ $0.245 |
| 全地端 Breeze(T4)+ Gemma 4 26B 本機 | **≈ $0.155 純 GPU**(無 API 費) |

**便宜到可以無腦跑,但不是 $0.10。** 譯那跳確實幾乎免費($0.005/hr,
Gemma 4 26B 對 gemini-3.5-flash 的 1/22),貴的是聽那跳。

## 7. 生態現況(選型時的背景)

- **做字幕的預設拿 ElevenLabs Scribe**(SubtitleAI、Outtake 直接用;
  What'Sub 高度疑似)。理由是詞級 + 字元級時間戳現成、audio event tagging、
  1,000 詞 keyterm
- **本地路線都收斂到 whisper.cpp / faster-whisper 家族**,GGUF/CT2 格式,
  Vulkan 或 CPU
- **Breeze 有 GGML 版**(`phate334/Breeze-ASR-26-GGML`),可走 whisper.cpp + Vulkan,
  跨 NVIDIA/AMD/Intel。HF 上另有 CT2(`phate334/Breeze-ASR-25-ct2`)、
  MLX(`eoleedi/Breeze-ASR-25-mlx`)、Core ML/ANE
  (`sheep52031/breeze-asr-25-coreml-ane`)等社群轉換版,**本專案一個都沒測過**
- **Qwen3-ASR** 是尚未評估的候選(1.7B,有 GGUF 與 OpenVINO,另有日語動漫特化版)

> ⚠️ **注意型號:上面那個 GGML 是 Breeze-ASR-**26**,而本專案所有數字都是
> `MediaTek-Research/Breeze-ASR-25`(revision `cffe7ccb`)量的。**
> HF 上已有 `Speech-AI-Research-Center/Breeze-ASR-26`。
> 26 的表現**未測**,不要把 25 的數字(中文 0.845、日文 0.415)套上去——
> 這正是 CLAUDE.md 鐵律 9 講的那類外推。

**Scribe 從未在 kikemu 的任何實驗中跑過** —— 與 Deepgram 並列為
「投報率最高的未執行實驗」,成本約 $0.20。

## 8. 建議的行動順序

1. **修 OpenCC 的語言判斷**(§5.1)—— 十分鐘,而且是潛在的沉默錯誤
2. **加 Scribe arm**(§7)—— $0.20,補上最大的評測空白
3. **詞表回流迴路**(§3)—— 把複核者的選擇自動變成下一場的詞表
4. **分歧率護欄**(§6.4)—— 三行程式碼,把已知失效點變成可執行規則
5. 事後那一趟接上 forced alignment(§2)—— 前提是拿得到音訊 bytes
   (先解決 §4 的 PRD §2 界線問題)
