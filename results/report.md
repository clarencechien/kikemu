# kikemu 聽譯引擎評測報告

兩個實驗、一份結論。

- **exp1 — 日文導覽解說**:自訂詞表值不值得成為產品核心?(原 `handoff.md`)
- **exp2 — 中英夾雜技術演講**:同一套詞表機制在語碼混合場景是否同樣有效?(原 `handoff-v2.md`)

原始資料:`results/raw/`(exp1)、`exp2/results/raw/`(exp2)。腳本:`scripts/`、`exp2/scripts/`。
選型速查:`results/stt-matrix.md`。

## 0. TL;DR

**兩個實驗合起來的核心判斷:一體式模型只在直接餵訊號的通道可用;
只要音訊經過空氣,就要用專用 ASR。而詞表值不值得做,取決於「引擎缺的是什麼」。**

| | exp1 日文導覽(專名) | exp2 中英夾雜演講(術語) |
|---|---|---|
| 最佳 arm | SM + 地點詞表 | SM `cmn_en` 雙語 pack(+ 投影片詞表) |
| **詞表邊際價值** | **+0.12 ~ +0.19(核心資產)** | +0.03 ~ +0.05(小加分) |
| 真正的槓桿 | 詞表 | **語言 pack(+0.23 ~ +0.29)** |
| 一體式乾淨條件 | 打平(0.836 vs 0.836) | 略勝(0.927 vs 0.833,CI 下緣壓 0) |
| 一體式崩潰點 | 人聲 8dB → 0.030(全滅) | 人聲 12dB → 0.396(半滅) |
| 在地化/不譯規則 | 原版 prompt 已解決 | 原版 prompt 已解決(P1 零增量) |

**三條可以直接用的規則:**

1. **一體式的門檻是「直接餵訊號」,不是「安靜」。** exp1 裡只加室內殘響、
   完全不加噪音,Gemini Live 就從 0.836 掉到 0.552,而 SM+詞表維持 0.836。
   手機桌上收音、講堂後排這種「聽起來還好」的情況已經出局。
2. **詞表投資判準:目標詞彙是「引擎沒見過的」(在地專名、料號)才值得做大;
   「引擎見過但模式不對」(通用英文術語)要先修語言設定,詞表只是小數點。**
3. **選 SM 路線的理由是抗噪與即時性,不是成本。** 見 §5 —— 兩跳架構的
   API 成本大約是一體式的兩倍,這點要如實對內說明。

**產品建議:kikemu 走 SM + 以地點自動生成詞表 + Gemini 翻譯。
只有能保證 line-in 級音源的通道才考慮降級為一體式,且切換須以現場 SNR 偵測把關
(人聲背景 SNR < 約 15dB 一律不可用)。廠區/會議線改用 `cmn_en` 雙語 pack,
詞表退為進階選項。**

## 1. 方法與信度控制

兩個實驗共用同一套 harness:目錄結構、統計處理、判定規則凍結流程一致。

### 1.1 語料

| | exp1 | exp2 |
|---|---|---|
| 來源 | 大阪觀光局「しっとんか大阪」音訊導覽(ON THE TRIP 製作) | 台大李宏毅 ML2021 / 生成式AI導論2024 |
| 選段 | 6 段(東大阪神道 ×2、堺茶道歷史 ×2、池田近代 ×2) | 3 段 × 5 分鐘(Self-attention / GAN / GenAI 導論) |
| 標準答案來源 | 官方頁面旁白全文 + 雙引擎驗證 | 無官方文字,三路轉寫 + 人工裁決 |
| 授權 | 僅私下評測,音檔不入庫不散布 | 同左;課程公開 ≠ 開放授權 |

### 1.2 標準答案:兩個實驗都不用單人聽寫

**exp1 — handoff 警告的三個陷阱全部命中:**

| 陷阱 | 實況 | 處理 |
|---|---|---|
| 頁面文字 ≠ 音檔內容 | 堺系列音檔只唸頁面文字的前 20~33%(節錄版) | 對齊找出實唸子區間,參考文本裁切 |
| 音檔與段落不是 1:1 | 枚岡神社 B-1/B-2 指向同一 mp3,實際只唸 B-1 | 參考文本只取 B-1 |
| 需人工核對逐字吻合 | 旁白會唸段落標題(頁面正文沒有);少數助詞增減 | 見下方協定 |

驗證協定:每段由兩個獨立引擎轉寫(Speechmatics batch、Gemini 3.5 Flash),
與頁面文字三方對齊,殘差逐條人工檢視(`corpus/reference/review.md`)。
規則 R1–R5 寫死在 `scripts/build_reference.py`,先於任何 arm 執行:

- 兩引擎**一致**而頁面**沒有**的插入(語氣詞「御」「の」)→ 採納
- 同音異寫差異(ことはじめ/事始、アメノコヤネノミコト/天児屋根命)→ **保留官方頁面寫法**,
  避免參考文本偏向任一 ASR 的選字習慣

結果:參考文本與兩引擎的 CER 為 SM 0.03~0.21、Gemini 0.04~0.14,
殘差人工檢視確認除標題與少數助詞外無內容性偏離。

**exp2 — 沒有官方文字,人工裁決比重更高:**

三路獨立轉寫(SM batch cmn、gemini-3.5-flash、gemini-3.6-flash),
以兩個 Gemini 的 token 級一致部分為基底,80 個分歧塊逐條檢視,裁決寫入 `overrides.json`。

**記錄在案的偏離:SM-cmn 不參與英文拼寫表決**——它在受測維度上系統性弱勢
(COVID-19 → 「CoffeeNight」、network → 「news」),讓它投票會污染正解。
但它的中文可靠,用於裁決中文區域:

- 「英年早逝」「火影忍者」「爆雷」——三方證據一致後修正
- **關鍵裁決:講者說的是「函式」不是 "function"**。gm35 把 10 處中文「函式」
  英文化成 function,SM 聽到 8 次 函式/函数 佐證。這同時暴露了
  **「用 LLM 做逐字稿會被它的正字法偏好污染」**這個方法論陷阱
- 數字讀法(one-hot 向量「1 0 0 0」)按實際唸法修正

### 1.3 正解清單與判定規則(執行前凍結)

**exp1 — 67 個專有名詞**(神名、人名、社名、神事名、地名、年代)。
Gemini 從已驗證參考文本抽取,程式強制 surface 必須逐字出現;
機械化整理規則寫死(去子字串重複、通用詞停用表、標題拼接假詞過濾)。

**exp2 — 86 個英文術語實例**(S1 26 個 51 次、S2 10 個 20 次、S3 6 個 16 次)。
機械抽取連續拉丁 token,排除純填充詞與數學式唸法。
每個術語另標 no_translate(架構名/專名/縮寫)或 may_translate(一般技術詞)。

**兩套判定規則並列,均寫死:**

- **strict**:與正解逐字相符(exp1 原規則;exp2 為大小寫不敏感完全相符)
- **tolerant**:另接受官方讀音、凍結的標準別寫法(exp1)/連字號空白折疊與凍結變體(exp2)

結論以 tolerant 為主、strict 為 robustness check;兩者排序一致。

|---|---|---|---|---|

### 1.5 聲學條件(真實材料,非合成噪音)

RIR 一律取自 MIT IR Survey,以 Schroeder 積分決定性挑選;噪音取自 DEMAND 實錄。
SNR 以**語音活動段 RMS** 計算(50ms 框、能量閘門 10% of max),不含靜音;
亂數種子固定,每步後峰值正規化。

**exp1(導覽場景)** — 6 段 × 5 條件 = 30 檔:

| 代號 | 處理 |
|---|---|
| N0 | 原始 |
| N1 | + RIR(T60 = 0.600s,`h213_SubwayStation`) |
| N2 / N3 | N1 + DEMAND PCAFETER 食堂人聲 @ SNR 15 / 8 dB |
| N4 | 帶通 300–3400Hz + 削波 + RIR(擴音喇叭) |

**exp2(講堂/會議場景)** — 3 段 × 4 條件 = 12 檔:

| 代號 | 處理 |
|---|---|
| M0 | 原始 |
| M1 | + RIR(T60 = 0.721s,`h100_Classroom`) |
| M2 | M1 + DEMAND OOFFICE @ SNR 20 dB |
| M3 | M1 + DEMAND OMEETING 會議交談 @ SNR 12 dB |

exp2 的 RIR 挑選規則加了空間類別約束(限 Classroom):
無限制時的最接近值是浴室——衰減對、空間錯。規則與理由一併記錄。

## 2. exp1 結果:日文導覽解說

### 2.1 專有名詞召回率矩陣(tolerant,67 個專名 micro-average)

| arm | N0 | N1 殘響 | N2 人群15dB | N3 人群8dB | N4 擴音 |
|---|---|---|---|---|---|
| A(Gemini Live) | 0.836 | 0.552 | 0.194 | **0.030** | 0.582 |
| C(SM 無詞表) | 0.716 | 0.687 | 0.672 | 0.433 | 0.687 |
| **C+(SM + 詞表)** | **0.836** | **0.836** | **0.806** | **0.627** | **0.851** |

strict 判定排序完全一致(A 0.716/0.478/0.149/0.015/0.537;
C 0.672/0.627/0.612/0.388/0.627;C+ 0.731/0.731/0.702/0.522/0.746)。
以「譯文中出現該專名」交叉檢核,排序亦不變。

### 2.1b 追加 arm `Abat`:那個「崩潰」是 Live 的行為,不是模型的能力上限

exp1~exp4 的「一體式」全部走 **Live API**。exp5 在同一批音檔上量到 Live 與
`generateContent` 差很多,於是回頭在 exp1 補跑 `Abat`
(`gemini-3.5-flash` + `generateContent`,`thinkingLevel: minimal`,
prompt 只要求逐字轉寫)。**exp1 是驗證這件事最乾淨的地方:參考文本來自
大阪觀光局頁面,不是任何受測引擎產生的,沒有主場偏差。**

| arm | N0 | N3 人群8dB | N4 擴音 |
|---|---|---|---|
| A(Gemini **Live**) | 0.836 | **0.030** | 0.582 |
| **Abat(Gemini **批次**)** | **0.940** | **0.567** | **0.896** |
| C+(SM 即時 + 詞表) | 0.836 | **0.627** | 0.851 |

CER 更能說明發生了什麼:

| arm | N0 | N3 人群8dB | N4 擴音 |
|---|---|---|---|
| A(Live) | 0.114 | **0.911** | 0.180 |
| Abat(批次) | **0.072** | 0.348 | **0.093** |
| C+(SM 即時 + 詞表) | 0.093 | **0.319** | 0.096 |

N3 的 Live CER 0.911——6 段裡 4 段 CER ≈ 1.0,也就是**輸出是空的**。
同一個檔給 `generateContent`,CER 是 0.348,與 SM 的 0.319 同級。

**所以「一體式在人聲背景下整段放棄」是 Live API 串流路徑的行為,不是模型聽不懂。**
`results/stt-matrix.md` 原本的頭條結論已據此改寫成「一體式**即時**不可用」。

> **⚠️ 這個推論後來要收窄(2026-08-19)。** 上面是從 **Gemini 一家**的
> Live vs 批次對比推出來的,樣本只有一個模型家族。
> §3F 的 `Xgma_ja` 給了反例:**Gemma 4 12B 是非串流的**(`generateContent`
> 式的單發推論),在 exp1 的 N3(人群 8dB)一樣崩到 **0.077**,
> 其中 `sakai05__N3` 輸出**完全是空的**(0.6 秒回傳空字串)。
>
> 所以正確的說法是:**「人聲背景下整段放棄」是某些模型的失效模式,與串流無關;
> 而 Gemini 這一家的 Live 介面確實比它的批次介面更容易觸發它。**
> Live vs 批次那個對比本身仍然成立(同一家模型、同一批音檔),
> 但不能外推成「所有非串流模型都不會崩」。

三個要一起記住的限定:

1. **人聲 8dB 下批次仍略輸 SM+詞表**(召回 0.567 vs 0.627,CER 0.348 vs 0.319),
   而且 Gemini 這一跳**沒有用任何詞表**。差距不大,但方向沒有反轉。
2. **乾淨與擴音失真條件下批次是全場最好**(0.940 / 0.896,CER 也最低),
   贏過 SM+詞表。
3. 批次**沒有 timestamp、沒有 diarization、不能串流**,所以這一格不改變 kikemu
   的選型——產品要即時。它改變的是「事後逐字稿」那一類應用的建議。

**未驗證**:LLM 有可能靠世界知識「猜」出沒聽清楚的專名。CER 沒有支持這個懷疑
(批次的 CER 與 SM 同級,不是低召回卻低 CER 的那種形狀),但**沒有做人工聽核**。

原始檔:`results/raw/Abat/`(18 檔,含 usage 與 wall time)。

### 2.1c 追加 arm `Xbrz_ja`:Breeze 在日文上輸一大截,但**不會整段放棄**

handoff-v8 §1 A。Breeze 是 kikemu 唯一推薦的地端引擎,但先前的證據全部來自
中文語料(exp2 有訓練污染、exp5 是中文領域外)——**日文從沒測過,
而 kikemu 的產品本業就是日文導覽**。設定與 exp2 Phase A 完全相同
(T4/fp16、`chunk_length_s=0`、revision `cffe7ccb`、`language` 不指定)。

| arm | N0 | N1 殘響 | N2 人群15dB | N3 人群8dB | N4 擴音 | 平均 |
|---|---|---|---|---|---|---|
| Gemini 批次 | **0.940** | **0.896** | **0.836** | 0.567 | **0.896** | **0.827** |
| SM 即時 + 詞表 | 0.836 | 0.836 | 0.806 | **0.627** | 0.851 | 0.791 |
| SM 批次 + 詞表 | 0.866 | 0.836 | 0.821 | 0.597 | 0.836 | 0.791 |
| SM 無詞表 | 0.716 | 0.687 | 0.672 | 0.433 | 0.687 | 0.639 |
| Gemini Live | 0.836 | 0.552 | 0.194 | 0.030 | 0.582 | 0.439 |
| **Breeze ASR 25** | 0.522 | 0.478 | 0.403 | 0.179 | 0.493 | **0.415** |

#### 判讀(handoff-v8 §4,規則先寫死)

規則設 Δ = Breeze 減 SM+詞表(`Cplus`),取五條件平均:

| 預先寫死的門檻 | 實測 |
|---|---|
| ≥ 0 → 地端推薦不必加語言限定 | |
| −0.10 ~ 0 → 標「日文略遜」 | |
| **< −0.10 → 地端推薦必須限定語言** | **Δ = −0.376 ← 落這格** |

**所以「Breeze 是地端首選」這句話必須加上語言限定:中文可,日文不可。**
它連沒有詞表的 SM(0.639)都輸 0.224。這不意外——Breeze 是
Whisper-large-v2 的**中文**微調,日文不是它的主場;但先前把它寫成
通用地端推薦,是證據不足的外推。

#### 但 N3 那格,它是唯一沒有放棄的

handoff-v8 §4 對 N3 另有一條單獨判準,結果與上面相反:

| N3(人群 8dB) | 空輸出 | 極短輸出 | 召回 |
|---|---|---|---|
| **Breeze ASR 25** | **0** | **0** | 0.179 |
| Gemma 4 12B | 1 | 0 | 0.077 |
| Gemini Live | **2** | 2 | 0.030 |

**規則寫的是「沒有空輸出且召回 > 0.1 → Breeze 不會整段放棄」——成立。**
它的輸出長度比在 N0 是 0.99、N3 是 1.07(範圍 0.90~1.52),
**一直在講話,只是講錯**;Gemini Live 是 6 段裡 4 段直接沉默。

這兩件事要一起讀:**Breeze 日文準確度差,但失效模式比較安全**——
它給你一份錯的稿子,不是一片空白。對「至少要有東西可以校對」的流程,
這個差別是實質的;對「沒人校對」的流程,幻覺比空白更危險。

### 2.2 詞表的邊際價值:C+ − C(核心數字)

| 條件 | Δ(tolerant) | 95% CI | McNemar(C+獨對 / C獨對) |
|---|---|---|---|
| N0 | **+0.119** | [+0.016, +0.211] | 8 / 0 |
| N1 | **+0.149** | [+0.056, +0.215] | 10 / 0 |
| N2 | **+0.134** | [+0.037, +0.211] | 9 / 0 |
| N3 | **+0.194** | [+0.138, +0.232] | 14 / 1 |
| N4 | **+0.164** | [+0.071, +0.234] | 11 / 0 |

- 所有條件 CI 排除 0,**愈吵價值愈大**
- McNemar 幾乎單向:詞表救回的詞幾乎沒有代價
- 質性例子(hig01 N0):C 寫「石切剣や神社絵馬伝 / 長脛彦 / 馬島での尊」,
  C+ 正確寫出「石切劔箭神社絵馬殿 / 長髄彦 / 可美真手命」

### 2.3 A − C+ 隨噪音的走勢

| 條件 | Δ | 95% CI | McNemar(A獨對 / C+獨對) |
|---|---|---|---|

### 2.1d 追加 arm:ElevenLabs Scribe v2(handoff-v10 S1 / S5)

Scribe 是做字幕的業界預設(SubtitleAI、Outtake 直接用),但**本專案從沒跑過**。
2026-08-20 補上,而且**一併補了詞表對齊控制組**——沒有它,這個比較沒有解釋力。

#### 為什麼一定要有控制組

| | Speechmatics | Scribe |
|---|---|---|
| 詞表容量 | 1000 詞 | **即時上限 50 詞 × 20 字元**;批次實測可吃 166 條 |
| 讀音標註 | ✅ `sounds_like`(全形假名) | ❌ **沒有對應機制** |

kikemu 的 exp1 詞表是逐地點 142~166 條、**每一條都帶假名讀音**。
直接比「Scribe + 50 詞」與「SM + 完整詞表 + 讀音」,量到的會是
**詞表容量與讀音的差,不是引擎的差**。所以另跑 `Cbplus50`
(SM 批次,同樣 50 條、且拿掉 `sounds_like`)當控制組。

#### 結果(tolerant 專名召回,335 實例 micro)

| arm | 全部 | N0 乾淨 | N3 人群 8dB |
|---|---|---|---|
| Gemini 批次(`Abat`) | **0.827** | **0.940** | 0.567 |
| **Scribe 批次 + 完整 166 詞** | **0.824** | 0.866 | **0.657** |
| **Scribe 批次 + 50 詞** | 0.800 | 0.866 | 0.642 |
| SM 批次 + 完整詞表 + 假名(`Cbplus`) | 0.791 | 0.866 | 0.597 |
| SM 即時 + 完整詞表(`Cplus`,現行產線) | 0.791 | 0.836 | 0.627 |
| **SM 批次 + 50 詞、無讀音(`Cbplus50`,控制組)** | **0.704** | 0.776 | 0.493 |
| SM 批次無詞表(`Cb`) | 0.642 | 0.746 | 0.418 |
| Gemini Live(`A`) | 0.439 | 0.836 | 0.030 |
| Breeze(`Xbrz_ja`) | 0.415 | 0.522 | 0.179 |

#### 判讀(handoff-v10 §4,規則先寫死)

設 A = Scribe + 50 詞、B = SM + 50 詞(控制組)、C = SM + 完整詞表。

| 量 | 值 | 意義 |
|---|---|---|
| **A − B** | **+0.096** | **引擎的差**(詞表已對齊)→ 規則第一列:**Scribe 的引擎在日文上比 SM 強** |
| C − B | +0.087 | **SM 完整詞表 + 假名讀音的總價值** |
| A − C | +0.009 | 現實的差:**帶著 50 詞的劣勢仍與現行產線打平** |

> **這兩個數字放在一起才是重點:Scribe 的引擎優勢(+0.096)
> 幾乎剛好抵掉 SM 整份詞表加讀音的價值(+0.087)。**

規則說 A − B ≥ +0.05 時「下一步是查它能不能吃更多詞」。查了:
**批次吃得下完整的 166 條**(50 / 100 / 166 都回 200),補跑後
**0.824,勝 `Cbplus` +0.033、N3 勝 +0.060**。50 詞那個上限只存在於即時。

#### N3(人群 8dB)是它最強的地方

那是全套語料唯一能觸發「整段放棄」的條件。Scribe **零空輸出、零極短輸出**,
召回 0.642(50 詞)/ 0.657(完整)——**全場該條件最高**,
而 Gemini 批次只有 0.567、Gemini Live 0.030。

引擎優勢也在這一格最大:**A − B 在 N3 是 +0.149**,N0 只有 +0.090。
**噪音越大,Scribe 的引擎優勢越明顯。**

#### 已知偏差與未做的事

1. **這一格全部是批次。** 主線(即時)的 Scribe v2 Realtime **尚未測**——
   它才是 SM 串流的直接競爭者。批次贏不等於即時贏。
2. **詞表對齊控制組只做了批次那半**(`Cbplus50`)。即時的控制組(SM 即時 + 50 詞)
   要等 S4 一起做。
3. **`Cbplus50` 取的是詞表的前 50 條**,不是「最有價值的 50 條」。
   照理挑選過的 50 條會更強,所以 B 這個基準**偏保守**,
   也就是 A − B = +0.096 **可能高估**了引擎的差。
4. Scribe 會輸出 **audio event 標記**(exp1 30 檔共 8 次,如 `[笑声]`)。
   計分前一律移除(規則寫在 handoff-v10 §4b,在跑之前定的),其他 arm 是 no-op。

### 2.1e Scribe **即時**:結論與批次相反,主線維持 SM(handoff-v10 S4)

§2.1d 量到 Scribe 的**批次**引擎在日文上勝 SM +0.096。但 kikemu 的主線是**即時**,
而 **Gemini 的教訓正是「批次好不代表即時好」**(§2.1b:批次 0.567 vs Live 0.030)。
所以即時這格單獨量,而且**一樣配了詞表對齊控制組**。

|---|---|---|---|---|---|---|
| **C** SM 即時 + 完整詞表+假名(`Cplus`,現行產線) | **0.791** | 0.836 | 0.836 | 0.806 | **0.627** | 0.851 |
| **B** SM 即時 + 50 詞、無讀音(`Cplus50`,控制組) | 0.699 | 0.746 | 0.776 | 0.716 | 0.478 | 0.776 |
| **A** Scribe v2 Realtime + 50 keyterms(`Srt_ja`) | 0.624 | 0.761 | 0.716 | 0.552 | 0.343 | 0.746 |
| SM 即時無詞表(`C`) | 0.639 | 0.716 | 0.687 | 0.672 | 0.433 | 0.687 |
| Gemini Live(`A`) | 0.439 | 0.836 | 0.552 | 0.194 | 0.030 | 0.582 |

#### 判讀(handoff-v10 §4,規則先寫死)

| 量 | 值 | 落點 |
|---|---|---|
| **A − B**(引擎,詞表已對齊) | **−0.075** | 第三列:**Scribe 引擎較弱 → 主線維持 SM,本格結案** |
| C − B(完整詞表 + 假名的價值) | +0.093 | 與批次那格的 +0.087 幾乎相同 |
| A − C(現實的差) | −0.167 | **< −0.10 → 不可用於本業**(混變因,不可單獨引用) |

#### 這一格最重要的發現:批次與即時是**不同的模型,而且方向相反**

| | 引擎的差 A − B |
|---|---|
| **批次**(`scribe_v2`) | **+0.096**(Scribe 較強) |
| **即時**(`scribe_v2_realtime`) | **−0.075**(Scribe 較弱) |

同一個廠商、同一批音檔、同一份 50 詞詞表、同一個控制組設計,
**批次贏 SM、即時輸 SM**。`scribe_v2` 與 `scribe_v2_realtime` 是兩顆不同的模型。

> **這是「批次好不代表即時好」的第二個廠商實例。** 第一個是 Gemini
> (批次 0.567 / Live 0.030,§2.1b)。兩次都是**即時那顆比較弱**。
> **選型時批次與即時必須分開量,不可互相外推**——這條現在有兩家的證據。

#### 另一個決定性的差異:commit 節奏差 23 倍

| | commit 間隔 | 每次定稿字數 | 定稿 p50 | 改寫率 |
|---|---|---|---|---|
| SM(`max_delay=2.0`) | **每 0.6 秒音訊** | 2.5 字 | 2.23s | **0.165** |
| **Scribe(VAD 預設)** | **每 13.7 秒音訊** | 56.2 字 | **1.76s** | **0.783** |

**Scribe 單次定稿到得比較快(1.76s vs 2.23s),但兩次定稿之間隔 13.7 秒。**
也就是說文字要 14 秒才凍結,而 SM 是 0.6 秒——這正是改寫率 0.783 vs 0.165 的來源
(已確認**不是** metric 假象:`sm_rewrite_rate` 在每次定稿時會重置,
commit 邊界沒有被算成回退;Scribe 是真的在段內反覆修改,
`奇襲会` → `岸周街道沿いに` → `奇襲街道沿いに南へ`)。

**對 kikemu 的兩層時間軸(暫定/定稿)是硬傷**:字幕會有 14 秒處於可改寫狀態。

⚠️ **但這是 `commit_strategy=vad` 的預設行為,不是模型的固有性質。**
API 有 `commit_strategy=manual` 與 `vad_silence_threshold_secs` /
`min_silence_duration_ms` 可調,**本專案沒有調校過**。
要下「Scribe 即時的字幕會跳」這個結論之前,應該先把 commit 節奏調到與
SM 的 0.6 秒同級再量一次(見侷限 24)。

#### 沒有整段放棄

N3(人群 8dB)六個檔:**Scribe、SM 三個 arm 全部零空輸出**;
只有 Gemini Live 是 **6/6 全空**。這與 §2.1b/§2.1c 的既有結論一致。

#### 產品結論

**kikemu 的日文即時主線維持 Speechmatics + 場景包詞表,不換。** 三個理由,
任一個單獨都足夠:

1. 引擎在即時上就輸(−0.075),不是詞表的問題;
2. 場景包是核心資產(完整詞表 + 假名值 +0.093),而 Scribe 即時**上限 50 詞、無讀音欄位**;
3. commit 節奏 13.7 秒,兩層時間軸接不上(可調但未驗)。

**但 Scribe 在非即時線上仍然是強候選**(§2.1d 日文 0.824、§3E.2 中英夾雜 0.921)。

## 3B. exp3 結果:快速前處理救不救得了一體式?(handoff-v3)

快速降噪,Gemini Live 能不能回到自己的 N0 水準(0.836)?

### 3B.1 前處理器與 RTF

| 手法 | 定位 | RTF(實測) |
|---|---|---|
| webrtc(APM NS level 3) | 官方採集端等價物(瀏覽器/OS 內建那套) | 0.001 |
| sg(譜門檻,1s 塊、僅用過去 2s 上下文) | 傳統法代表,因果模擬 | 0.028 |
| blend(0.75·增強+0.25·原始) | 假影感知混合(Iwamoto 2022) | 0.002 |

RNNoise 未測(pyrnnoise 與環境 PyAV 不相容,記錄缺口)。
全部遠低於 0.3 的即時門檻——「快」不是問題,問題在效果。

### 3B.3 判讀(對照 handoff-v3 §5 預先寫死的判讀表)

1. **A@N3+pp < 0.2 → 快速降噪救不了 babble,維持原架構結論。**
   最有戲的一刻是譜門檻讓四個原本整段放棄的 N3 檔案重新開口
   (ikeda02 輸出 0→237 字元)——**但召回率是 0.000,CER 0.891**:
   模型開口了,講的都不是原文。降噪打破了「VAD 看不見語音」的癱瘓,
   卻救不回底層辨識——因為譜門檻除不掉「頻譜跟前景一樣」的人聲,
   只是把混合訊號變成另一種模型沒見過的訊號
2. **webrtc 在乾淨音源上有假影傷害**(N0 0.836→0.791)——
   假影文獻(CHiME、Iwamoto 2022)的預測應驗;
   任何部署都必須 SNR 門控,不能全程開著(Google 自家 VoiceFilter-Lite 同款設計)
3. **SM+pp − SM ≈ 0 到負**(N3:webrtc −0.03、sg −0.09、blend −0.10)。
   配合 exp1 的「批次 ≈ 即時」證據,**「SM 只是在 endpoint 後串了前處理」
   假說不成立**:它的抗噪是聲學模型內建的(訓練時多條件增強),
   外掛前處理買不到,吵雜下反而扣分
4. blend × N3 依判讀表免跑:兩個基底手法都失敗,線性混合只會朝原始(0.030)靠攏

### 3B.4 結論

**「為什麼官方不做」的答案經實測後成立:**因為在推論端串快速降噪,
對訓練時已見過噪音的模型(SM)是零到負效果,對沒見過的模型(Gemini Live)
救不回正確性、還傷乾淨音源。降噪要嘛做在**採集端物理層**(指向性麥克風、
近講)、要嘛做在**訓練時**(多條件增強),推論前的軟體補救兩頭不討好。

kikemu 的架構結論不變且更穩固:**吵雜場景的解是換引擎(SM),
不是幫一體式模型加前處理。** 手機遠場收音的產品面改善方向是
物理的(麥克風選型、拾音距離),不是 DSP 的。

## 3C. exp4 結果:指向性拾音——Speak2 級夠不夠,還是要領夾麥?(handoff-v4)

方法:把拾音硬體翻譯成 (ΔDRR, ΔSNR) 聲學參數,對既有加噪檔做配對重合成

card 心形1m(+5,+3)、conf Speak2級陣列1.5m(+9,+6)、lav 領夾0.3m(+18,+15)。

### 3C.3 判讀(對照 handoff-v4 §4 預寫死的判讀表)

1. **Speak2 級救不回一體式(導覽場景)**:A@N3+conf = 0.284 < 0.5 ✗
2. **連領夾麥也只救一半**:A@N3+lav = 0.507 < 0.75 的門檻——
   即使模擬給了 +18dB DRR / +15dB SNR 的樂觀條件,一體式仍到不了可用區。
   殘餘 23dB SNR 的人聲仍讓它掉四成——**一體式對人聲背景的敏感度
   遠超出「改善拾音」能補償的範圍**
3. **最有力的一行對照:SM+詞表「不加任何指向性」(0.627)仍勝過
   A+領夾麥(0.507)。** 架構結論第三度加固
4. **SM 吃得到指向性紅利**(判讀表:C+@N3+conf − C+@N3 = +0.19 ≥ +0.1 ✓):
   conf 0.791、lav 0.821,貼到自己的無噪天花板。**好麥克風的錢應該花在
   SM 這條線上**——與 exp3(外掛 DSP −0.09)成完整對比:
   物理 SNR 改善有效,軟體降噪無效
5. **manemu/Speak2:落在判讀表的中間帶**。G@M3+conf = 0.604
   (「值得」門檻 0.75 ✗、「不必買」門檻 0.6 也未跌破)。
   誠實的讀法:M2(一般會議室)+conf 從 0.792 → 0.865,回到接近乾淨水準,
   **這一段 Speak2 是值得的**;M3(多人交談進行中)只回到 0.604,
   與 SM 打平——會議正熱時一體式仍不舒適。
   **manemu 的近場對話本體(≈M0)不需要 Speak2;
   要在會議室桌面用 manemu,Speak2 讓它在非尖峰時段可用**

### 3C.4 結論

**導覽線(kikemu):指向性能讓 SM 更好,救不了一體式。**
散客遠場的正解維持 SM+詞表;若能讓導覽員戴領夾麥,SM 到 0.82+,
且此時甚至還輪不到考慮一體式(它連領夾都只有 0.507)。

**會議線(manemu):Speak2 級會議麥值得配,但買它是為了「把一般會議室
變成乾淨音源」,不是為了救多人交談尖峰**——尖峰時段仍是 SM 的場子。

**全部為聲學模擬,樂觀上緣。「conf/lav 不夠」的結論可信;
「SM+lav = 0.82」這類正向數字若要作為採購依據,需真機驗證。**

## 3D. exp2 追加 arm:Breeze ASR 25(X-breeze)— Phase A 快篩

**問題**:針對台灣華語與中英夾雜微調的開源模型(Whisper-large-v2 微調,Apache 2.0),

量的是**純模型能力**——exp2 回答了「詞表值多少錢」,這一格回答「模型調校值多少錢」。

跑法見 `notebooks/breeze_asr25.ipynb`(Colab T4,fp16,`chunk_length_s=0` sequential,
模型 revision 釘死)。音檔由 `exp2/scripts/degrade.py` 現場重建並對 SHA256,
與其他 arm 位元相同。

### 結果(tolerant 召回;Phase A = S1-M0 / S1-M3 / S3-M0)

| arm | S1-M0 乾淨 | S1-M3 +交談 12dB | S3-M0 乾淨 | 合計 |
|---|---|---|---|---|
| X_bi(SM 雙語,無詞表) | 0.848 | 0.475 | 0.438 | 0.634 |
| Xsli_bi(SM 雙語 + 投影片詞表) | 0.881 | 0.542 | 0.438 | 0.679 |
| G(Gemini Live 一體式) | 0.898 | 0.424 | 0.938 | 0.694 |
| **X-breeze(無詞表)** | **0.949** | **0.780** | 0.875 | **0.866** |

**三個檔全部領先,而且最大的贏面在最吵的條件**:M3 上 +0.31 對 X_bi、
+0.24 對 Xsli_bi(**贏過配了詞表的 Speechmatics**)、+0.36 對 Gemini Live。

**預先登記的疑慮沒有發生。** 事前擔心「中文訓練資料全為合成語音,真實噪音下會崩」——
沒有崩,它反而是抗噪最好的一個 arm。

### 但它有一個 Whisper 家族的老毛病

M3 的轉寫裡有一段 **`,000,000,000` 重複 167 次**的迴圈(189 字元,三段),
觸發點是講者唸 one-hot vector 的「1 後面很多個 0」。M0 兩個檔都沒有這個問題。

| S1-M3 | TER | CJK 字元比 |
|---|---|---|
| 原始輸出 | 0.380 | 0.81 |
| 收掉重複迴圈後 | **0.261** | 0.92 |
| (對照)X_bi | 0.290 | 0.96 |
| (對照)Xsli_bi | 0.265 | 0.96 |
| (對照)G | 0.807 | 0.89 |

**術語召回不是靠這段垃圾灌出來的**:收掉重複前後,字面命中的術語種數都是 15/26,
完全沒變(重複的內容是數字,不會誤中任何英文術語)。收掉之後 TER 0.261 也是全場最佳。
所以正確的說法是:**轉寫品質很好,但有一個局部、可偵測、可後處理的重複迴圈**——
產品要用它的話,加一個「連續重複 n-gram 就截斷」的後處理即可,這是 Whisper 生態的標準做法。

### `language` 參數:沒有差別(且原因查得出來)

`language=None`(自動偵測)與 `language="zh"` 的輸出**位元完全相同**(三個檔皆是,
耗時不同證明兩趟都真的跑了)。原因在模型的 `generation_config.json`:
`forced_decoder_ids: [[1, None], [2, 50359]]` —— 語言槽是 `None`(留給自動偵測)、
task 固定 transcribe。這批音訊自動偵測本來就判成中文,所以指不指定沒有差。

⚠️ **尚未排除的另一種解釋**:transformers 5.13 可能根本沒把 `generate_kwargs` 的
language 吃進去。要排除很便宜——拿一個檔跑 `language="en"`,輸出若改變就證明參數有效。
Phase B 前補這一槍。

### 這一格改變了 exp2 的結論嗎

改變了一半。exp2 說「中英夾雜的槓桿是語言 pack(+0.23~0.29),詞表只是小加分」——
X-breeze 顯示**還有第三個更大的槓桿:換一個為這個語域微調過的模型**,
它在無詞表的情況下贏過「雙語 pack + 詞表」的組合。

但先別急著改架構,見下面的偏誤警告。

### 🚨 訓練資料污染(不是「疑似偏誤」,是已證實)

查 Breeze ASR 25 的模型卡,訓練資料組成是:

| 來源 | 時數 | 性質 |
|---|---|---|
| ODC Synth | 10,000 hr | 合成中文(FineWeb2 文本 + BreezyVoice TTS)|
| CommonVoice17-EN | 1,738 hr | 真實英文 |
| **NTUML2021** | **11 hr** | **真實中英夾雜** |

**`NTUML2021` = 台大機器學習 2021 = 本評測 S1(自注意力)與 S2(GAN)的來源課程。**
也就是說,**這個模型是在我們的評測語料上微調過的**。這不是「團隊熟悉這個語域」的
軟性偏誤,是直接的訓練/測試污染。(致謝名單裡的李宏毅教授指導,只是同一件事的表面。)

**Phase A 的數字本身就洩漏了這件事**:

| 檔 | 來源課程 | X-breeze | G(Gemini Live) | |
|---|---|---|---|---|
| S1-M0 | **ML2021**(在訓練集內) | **0.949** | 0.898 | Breeze 贏 |

(單點觀察,不是證明:S3 只有一個檔,且兩門課同一位講者、語域相近。)

### 這一格現在能說什麼、不能說什麼(**已依 exp5 重寫**,handoff-v6 §6)

下面是 Phase A + exp5 合併後的版本。標 ⟳ 的是 exp5 讓結論**改變**的項目。

**能說**:
- **抗噪優勢是真的,而且撐過了領域外檢驗。** Phase A 在 M3 量到 0.780
  vs 全部 SM arm 的 0.42~0.54;exp5 換一批模型沒看過的語料,M3 仍有 **0.810**,
  贏 SM batch **+0.165** [+0.074, +0.222],CI 不含 0(§3E)。
  記住逐字內容不會讓模型在噪音下更會聽——這條推理站住了。
- ⟳ **「Breeze 在中英夾雜上贏過 Speechmatics」現在可以說了**,但要帶條件:
  領域外 Δ = **+0.146** [+0.111, +0.185];換成 SM realtime 基準約 **+0.09**。

**一句話版本:Breeze 的價值不是「最準」也不是「最耐吵」,

### 3E.4 判讀(對照 handoff-v6 §5 預先寫死的判讀表)

規則設 Δ = Breeze 減 SM 的 tolerant 召回:

| 預先寫死的門檻 | 實測 |
|---|---|
| ≥ +0.15 且 M3 仍領先 → 優勢可推廣 | |
| **+0.05 ~ +0.15 → 有優勢但被污染放大** | **Δ = +0.146 ← 落這格** |
| ≈ 0 或為負 → 領先主要來自污染 | |

而且這個 +0.146 **還是偏高的估計**:規則寫的基準是 `X_bi`(realtime),exp5 的 SM
主要跑 batch;在唯一兩者都跑過的檔(T1__M0)上 realtime 比 batch **高 0.057**。
換算成 realtime 基準,Δ 大約是 **+0.09**,更深入中間那一格。

對照 Phase A(污染語料)的 Δ = **+0.281**:**去掉污染後優勢掉到約一半,
換成 realtime 基準則掉到約三分之一。**

**結論:Phase A 的領先有真實成分,但被訓練污染放大了大約 2~3 倍。
Breeze 是「領域內強、領域外小贏」,不足以改變 kikemu 的架構選擇。**

### 3E.5 但 M3 那一格是真的

handoff-v6 §5 特別交代 M3 要單獨看,理由是「記住逐字內容不會讓模型在噪音下更會聽」。
實測站得住:

- Breeze 在 M3 上贏 SM batch **+0.165**,贏 Gemini Live **+0.259**(CI 都不含 0)。
- Gemini Live 從 M0 的 0.930 掉到 M3 的 **0.551**(掉 0.379);
  Breeze 只從 0.880 掉到 0.810(**掉 0.070**)。
- TER 同向:Breeze 0.161 平均,SM batch 0.202,Gemini Live 0.313。

**但不要把這讀成「Breeze 抗噪最強」——它不是。** M3 的全 arm 排名:

| arm | M3 | M0→M3 掉幅 |
|---|---|---|
| Gemini 3.7-flash batch ※ | **0.880** | 0.082 |
| Gemini 3.5-flash batch ※ | 0.816 | 0.171 |
| Breeze ASR 25 | 0.810 | **0.070** |
| Speechmatics batch | 0.646 | 0.107 |
| Gemini 3.1 Live | 0.551 | 0.379 |

Breeze 在 M3 贏的是 **SM 與 Gemini Live**;Gemini `generateContent` 與它打平(3.5)
或贏它(3.7)。那兩格有主場優勢(§3E.7),但 3.7-flash **沒有參與造參考**,
所以 0.880 不能當成純粹的自我比對打掉。Breeze 唯一穩坐第一的是**掉幅**,
而 3.7-flash 的 0.082 也很接近。

**所以 Breeze 不可替代的地方不是抗噪排名,而是「唯一能地端跑,而且抗噪夠好」**
(Apache 2.0)。另外兩家都是雲端 API,音訊一定要送出去。

失效模式指向它為什麼耐吵:Breeze 的 F1(整段漏聽)只有 12,SM batch 是 37;
但 Breeze 的 F2(聽成別的詞)有 36,接近 SM 的 37——**它很少放棄,但常聽錯**。

### 3E.5b 即時與非即時的最佳解剛好相反

同一家、同一批音檔,Live 版在噪音下崩得最兇:

| | M0 | M3 |
|---|---|---|
| Gemini **Live**(3.1-flash-live-preview) | **0.930**(即時裡最好) | **0.551**(全場最差) |
| Gemini **batch**(3.5 / 3.7-flash) | 0.987 / 0.962 | 0.816 / 0.880 |

**注意 3.5-flash 沒有 Live 端點**,Live 與 batch 是不同模型、不同 API,不能合稱。

實務選型:

| 情境 | 選誰 | 理由 |
|---|---|---|
| 即時 + 安靜 | Gemini Live | M0 0.930 |
| 即時 + 吵(**kikemu 的情況**) | **Speechmatics** | M3 0.646 vs Live 0.551 |

## 3F. 案外案:Gemma 4 能不能取代?(2026-08-19)

### 3F.1 第一跳(聽)—— 拿不到,不是拿不動

Gemma 4 的音訊能力**只在部分變體上**。HF 的 tag 直接分野:

| 變體 | HF pipeline tag | 音訊 | 本環境 API |
|---|---|---|---|
| `gemma-4-E2B-it` / `E4B-it` / `12B-it` | `any-to-any` | ✅ | ❌ 三個端點都沒有 |
| `gemma-4-26B-A4B-it` / `31B-it` | `image-text-to-text` | ❌ | ✅ AI Studio + OpenRouter |

**能服務的兩個沒有音訊,有音訊的三個沒有端點。** 實測 400:

```
gemma-4-31b-it      "Audio input modality is not enabled for this model"
gemma-4-26b-a4b-it  同上
```

三條路都查過:AI Studio 的 50 個模型只有那兩個 Gemma;OpenRouter(key 有效,
可見 415 個模型)上的 Gemma 4 input modality 是 `image/text/video`,沒有 audio;
`CLOUDSDK_AUTH_ACCESS_TOKEN` 是 proxy 佔位字串,Vertex 進不去。

**所以「12B 先 ASR」這一跳無法用 API 驗證。** 要驗只能地端跑,而本機
(4 核 CPU、15 GB RAM、22 GB 磁碟)只放得下 `E2B`(權重 10.2 GB);
`12B-it`(`Gemma4UnifiedForConditionalGeneration`,23.9 GB)**裝不下**。

**出路已備妥:** [`notebooks/gemma4_12b_exp5.ipynb`](../notebooks/gemma4_12b_exp5.ipynb)
——Colab 一鍵跑,語料用 exp5(Breeze / Gemini 批次 / Gemini Live / SM 四個 arm
都在同一批檔案上跑過),最後一格直接印出五方對照。**arm 代號 `Xgma_12b`,
`score.py` 與 `compare.py` 已經認得它,結果回填即可。**

三個接線細節已先在本機驗過(模型載不下,但 processor 路徑可驗):

- `Gemma4UnifiedProcessor` **需要 `torchvision`**(連帶 import image processor),
  少裝會噴看不懂的 `ModuleNotFoundError`。
- `apply_chat_template` 的 `enable_thinking` **預設就是 `False`**,
  關閉時送出一個立刻閉合的 `<|channel>thought\n<channel|>`——
  等同 API 端的 `thinkingLevel: "minimal"`。
- 28 秒音檔 → 698 個 audio frame(約 25 frame/秒),
  5 分鐘約 7500,遠低於 262k context,**不需要切塊**。

**三件事:**

> 若在別處看到 0.056,那是舊的段平均值,結論不變但數字對不上這裡。

**這個數字是真的,但它量的不是「聽力」。** 機制看輸出統計就清楚:

| arm | 拉丁字母佔比 | 平均輸出長度 | 每檔最長跳針 |
|---|---|---|---|
| **參考文本** | **17.52%** | **1808 字** | — |
| Breeze | 17.06% | 1744 | 0 |
| Gemini 批次 | 14.03% | 1905 | 0 |
| SM batch | 8.99% | 2457 | 0 |
| Gemini Live | 8.77% | 3213 | 7 |
| **Gemma 4 12B** | 9.32% | **4513** | **817** |

**輸出長度是參考的 2.5 倍,每個檔平均有 817 字的純重複迴圈。**
術語召回接近零是兩件事疊加:大量幻覺灌水,加上把英文音譯掉
(`data` → 「大河」/「對話」,`pipeline` → 「排隊」,`team` → 「聽音」)。

### 3F.2c 這**不是**「Gemma 4 聽力差」——設定已用官方樣本驗證

跑出爛結果時,第一件事是排除「我不會用」。拿模型卡自己 snippet 裡的
`journal1.wav` 跑同一套程式碼:

| prompt | 輸出 |
|---|---|
| **官方原版** | `I woke up early today feeling refreshed. The morning light was beautiful and I enjoyed a nice cup of coffee.` — **完美** |
| 官方 + 自加「保留英文」 | `我可非常好, today feelingly fresh. The morning light was beautiful…` — **被弄壞** |

**兩個結論:**

1. **設定正確。** 官方樣本轉寫完美,所以 exp5 上的爛結果是**語料契合度**問題,
   不是通用能力問題。
2. **不要改官方 prompt。** 我在官方 prompt 後面加一句「保留原樣英文」,
   同一段乾淨英文音訊就開始幻覺中文、把 `feeling refreshed` 弄成
   `feelingly fresh`。**這個模型對 prompt 偏離極度敏感**——而 exp5 量的正是
   英文術語保留,原本最想加的就是那句話。這一格因此**無解**:
   加了指示會壞,不加就音譯掉。

### 3F.2d 三條 handicap(其他 arm 都沒有)

判讀 0.028 時必須連這三條一起讀:

1. **30 秒硬切,無重疊。** 模型卡 §7 的硬性上限,不是我們選的。
   5 分鐘要切 10 塊,塊與塊之間**沒有任何上下文**——對連續對話特別不利。
   其他所有 arm 都是整段處理。
2. **prompt 是英文官方模板**,而語料是中英夾雜的台灣華語。改不得(見上)。
3. **輸出繁簡混雜**(`伊达衮帝地`、`政府腐`、`对水印斯`),
   評分有做簡繁折疊所以不影響召回,但反映輸出不穩定。

### 3F.2f 變因拆解:不是切塊、不是夾雜,是**自發口語的中文**

exp5 的 0.028 同時混了四個變因,分三組拆開(第四個變因**模型型號**見 §3F.2g):

| 組 | 語言 | 語體 | 切塊 | Gemma 4 12B | 對照 |
|---|---|---|---|---|---|
| 模型卡樣本 `journal1.wav` | 英文 | 唸稿獨白 | 不用 | **完美** | — |
| exp1 控制組(`Xgma_ja`) | 日文 | 唸稿旁白 | 部分要切 | 召回 **0.272**(6 段) | SM+詞表 0.791 |
| exp5 主表(`Xgma_12b`) | 中英夾雜 | 自發對話 | 30s × 10 | 召回 **0.028** | Breeze 0.845 |
| **純中文視窗**(`Zgma`) | **中文** | 自發對話 | **不用** | **CER 2.231** | Breeze 0.198 |

**第三組是關鍵:拿掉夾雜、拿掉切塊、給它 20 秒乾淨片段,它還是崩。**
所以切塊與語碼轉換都不是主因。

#### 純中文 20 秒視窗:四方對照(CER,越低越好)

| arm | n | CER 平均 | CER 最差 | 輸出長度 / 參考長度 |
|---|---|---|---|---|
| **Breeze ASR 25**(地端) | 8 | **0.198** | 0.628 | 1.06 |
| ElevenLabs Scribe v2 | 8 | 0.333 | 0.821 | 1.27 |
| Speechmatics 批次 | 8 | 0.206 | 0.474 | 1.03 |
| Gemini 3.5 批次 | 8 | 0.263 | 0.744 | 1.21 |
| **Gemma 4 12B** | 8 | **2.231** | 6.833 | **2.21** |

**CER 2.231 代表編輯距離是參考長度的 2.2 倍——比整份刪掉還糟**,
因為它多吐了 2.21 倍的字。這不是「差一點」,是輸出不可用。

**這一格也給了地端一個好消息**:Breeze 在純中文短片段上 **0.198,全場最低**,
略勝 Speechmatics。地端不是只能將就。

#### ⚠️ 這個 CER 有一個系統性偏差:它懲罰標點(2026-08-20 發現)

**純中文視窗的參考文本完全沒有標點**(逐窗約 100 字、0 個標點,因為 exp5 的
參考是連續字串),而 CER 的 tokenizer 把**每一個標點都算成一個 token**——
所以會輸出標點的引擎每個檔平白多背 8~12 個插入。

| arm | 原樣(本報告採用) | 兩邊都去標點 | 標點數/檔 |
|---|---|---|---|
| Breeze | **0.198** | 0.198 | 0 |
| SM 批次 | 0.206 | 0.206 | 0 |
| Gemini 3.5 批次 | 0.263 | **0.159** | 11 |
| Gemma 4 E4B(貪婪) | 0.295 | 0.213 | 8 |
| ElevenLabs Scribe v2 | 0.333 | 0.205 | 12 |

**去掉標點之後名次會變**:Gemini 從第 3 變第 1,Scribe 從第 5 變成與
Breeze / SM 三者幾乎並列。

**揭露先後順序(重要):這個偏差是在看到 Scribe 的分數之後才發現的。**
所以本報告的主數字**維持原樣的 CER**(那是 exp5 一開始就在用的算法),
上表右欄是**事後敏感度分析**,不是主結果。

**但它影響的不只是 Scribe**:先前寫的「Breeze 在純中文短片段上 CER 全場最低」
只在含標點的算法下成立;去標點後 **Gemini 批次的 0.159 才是最低**。
Breeze 勝 SM(0.198 vs 0.206)那一條不受影響——兩者都不輸出標點。
見侷限 16r。

**給後續實驗的建議**:純中文視窗那組若要再用,**應改用去標點的 CER**,
並在報告裡標明換過算法;不要在同一張表裡混用兩種。

#### 視窗怎麼挑的(規則先寫死)

`exp5/scripts/cut_zh_windows.py`。exp5 語料是中英夾雜,但夾雜是**局部**的——
整段裡有大片沒講到英文的地方,切出來就是天然的純中文語料。

- 定位靠 Speechmatics 批次的**詞級時間戳**(job id 存在既有結果裡,重抓免費)
- 20 秒視窗、起點每 5 秒掃一次、貪婪不重疊、音源用 M0
- 參考文本用 SequenceMatcher 把 SM 詞流對齊到 exp5 參考再切片
  (與 `build_reference.py::sm_align()` 同一個做法)
- **SM 的轉寫與對齊出的參考,兩邊都不能含拉丁字母**——初版只檢查前者,
  漏掉 SM 把 `Mario` / `DevCore` 聽成中文的視窗;規則**在跑任何模型之前**補嚴,
  12 個視窗因此收斂成 8 個

指標用 CER 不用術語召回:這些視窗刻意挑成沒有英文,沒有術語可召回。

#### ⚠️ 有一個變因我沒能拆開

**語體與語言在這三組裡是綁在一起的**:英文樣本是唸稿、日文 exp1 是唸稿旁白、
中文視窗是自發對話(有嗯啊、重複、話沒說完)。所以**不能**說
「Gemma 4 中文特別差」,只能說:

> **Gemma 4 12B 在自發口語的台灣華語上不可用。**

要分開需要一份**唸稿型中文**語料——那是新語料,切現有的解決不了。

### 3F.2g 模型大小才是主因:E4B 比 12B 好一個數量級(handoff-v8 §2 C)

§4 C 的假說先寫死:「12B 的 CER 2.231 有大量幻覺灌水(輸出長度 2.21 倍),
**小模型的幻覺傾向常常較低**,E4B 可能反而穩。」

Gemma 4 有三個含音訊的變體(`E2B` / `E4B` / `12B-it`,HF tag `any-to-any`)。
拿 **E4B** 跑**完全相同**的三組語料、相同的官方 prompt、相同的解碼參數
(只有 GPU 從 A100 換成 L4,因為模型小很多):

| 語料 | **Gemma 4 E4B** | Gemma 4 12B | 同批最佳 |
|---|---|---|---|
| exp5 中英夾雜 M0 / M3 | **0.741 / 0.627** | 0.044 / 0.013 | Breeze 0.880 / 0.810 |
| 純中文 20 秒視窗(CER) | **0.312** | 2.231 | Breeze 0.198 |
| exp1 日文 sakai 兩段 | **0.400** | 0.323 | SM+詞表 0.969 |

（arm `Xgma_e4b` / `Zgma_e4b` / `Xgma_ja_e4b`;exp1 那列刻意只取 sakai 兩段,
與 12B 是同一個子集,不受 §3F.2h 補跑的長段影響。）

**輸出長度比揭穿了機制:**

| arm | exp5 長度比 | 純中文視窗長度比 |
|---|---|---|
| 參考 = 1.00 | — | — |
| **Gemma 4 E4B** | **1.04** | **1.18** |
| Gemma 4 12B | 2.22 | 2.21 |
| Breeze | 0.92 | 1.06 |
| SM batch | 0.91 | 1.03 |

E4B 的輸出長度**幾乎正好等於參考**(1.04)。12B 是 2.22 倍。
看同一個檔(`T1__M0`)的原始輸出就完全清楚了:

> **12B**:「在法院的意見書,作者對政府,政府,政府,政府,政府,……」
> ——「政府」重複上百次,5145 字。
>
> **E4B**:「主要是工業園區,說這個工業園區是那種完全照新加坡那種建築的風格,
> 然後就是有靈力中心什麼,整個住宅很乾淨很舒適……那所以你這邊就是剛剛講做這個
> search engine 對……我在非常酷的聽,就應該整個並就如果從 indexing 這樣算的話」
> ——2236 字,可讀,英文術語原樣保留(有錯:`team`→「聽」、`core`→「酷」、
> 鄰里→靈力,但那是聽錯,不是壞掉)。

**所以 §3F.2b 量到的 0.028 不是聽力,是退化生成(degenerate generation)。**
12B 在這批語料上會掉進重複迴圈;E4B 不會。

#### 判讀(對照 §4 C 預先寫死的兩張表)

**第一張(長度比,決定假說本身):** E4B 是 1.04 / 1.18,遠低於門檻 1.4
→ **假說的前半成立**,幻覺確實隨模型變小而降。

**第二張(準確度門檻):** 規則寫的是「三組**都**跨過 → 收窄成 12B 不能聽」。
實測是**兩過一沒過**:

| 語料 | 門檻 | 實測 | |
|---|---|---|---|
| exp5 | ≥ 0.30 | 0.741 / 0.627 | ✅ |
| 純中文視窗 | CER ≤ 0.50 | 0.312 | ✅ |
| exp1 日文 | ≥ 0.60 | 0.400 | ❌ |

**規則沒有涵蓋這個落點,而且不臨場改門檻**(與 §2.1c 的 N3 同樣處理)。
照實記成**語言條件式**的結論:

> **中文**:「Gemma 4 不能聽」是錯的,**不能聽的是 12B**。E4B 在中英夾雜上
> 0.68 平均,已經與 Speechmatics batch(0.699)同級,只輸 Breeze 一截。
>
> **日文**:E4B 雖然比 12B 好(0.400 vs 0.323),但**沒有跨過門檻**,
> 對 SM+詞表的 0.969 還差得遠。**日文仍然不可用。**

規則另有一條「三組都跨過 → 補測 E2B」。三組沒有都跨過,所以**這次不補測 E2B**。

#### 這一格改寫了什麼

1. `stt-matrix.md` §6 的「❌ Gemma 4 不能拿來聽」**要改**——那是 12B 的結論。
2. §3F.2f 的變因拆解結論「不是切塊、不是夾雜,是自發口語的中文」**要再加一項**:
   **模型大小**,而且它的效應比前三個變因加起來都大。
3. §3F.2c「設定已用官方樣本驗證」仍然成立且更有價值——E4B 也先跑了
   `journal1.wav`(轉寫完美)才往下跑,兩個模型的基準線是同一條。
4. **「更大的模型更準」在這裡是錯的。** 12B 比 E4B 大約 3 倍,結果差一個數量級。
   評估開源模型時不要用參數量當代理指標。

⚠️ **仍未拆開的變因**:E4B 與 12B 不只大小不同,訓練配方也可能不同
(Google 沒有公開兩者的音訊資料差異)。所以正確的說法是
**「E4B 這個型號比 12B 這個型號好」**,不是「小模型一定比較好」。

### 3F.2i E2B:趨勢不是單調的,而且揭穿了一個方法問題(handoff-v8 §4 C-bis / C-ter)

§4 C 的規則寫「三組門檻都跨過才補測 E2B」,實測兩過一沒過,所以照規則沒跑。
**這一格是使用者指定補的**——規則管自動觸發,不管使用者指定。

E4B 讓「小模型幻覺較低」成立,所以 E2B 問的是新問題:**這個趨勢是單調的,
還是有甜蜜點?**

| 語料 | **E2B** | E4B | 12B |
|---|---|---|---|
| exp5 中英夾雜 M0 / M3 | 0.734 / 0.582 | **0.741 / 0.627** | 0.044 / 0.013 |
| exp1 日文(sakai 兩段) | 0.385 | **0.400** | 0.323 |
| **純中文 20 秒視窗(CER)** | **0.894** | **0.312** | 2.231 |
| exp5 輸出長度比 | 1.03 | 1.04 | 2.22 |
| **純中文視窗長度比** | **0.35** | 1.18 | 2.21 |

前兩組 E2B 與 E4B 幾乎平手(差 0.007~0.045,都在 §4 C-bis 寫死的 ±0.05 內)。
**但純中文視窗那組整個崩了,而且是用一種新的方式崩的。**

#### 三種失效模式,不是一種

| 模型 | 失效模式 | 長度比 |
|---|---|---|
| 12B | **吐太多**——退化生成,重複迴圈 | 2.21~2.22 |
| **E2B** | **整段放棄**——直接輸出結束符 | **0.35** |
| E4B | 兩者都沒有 | 1.04~1.18 |

E2B 在 8 個視窗裡有 **6 個輸出完全是空的**(E4B 與 12B 都是 0 個)。

#### 先排除自己的 bug,再排除取樣抖動

**空輸出第一個要問的是「模型真的不吐,還是我們的解析把它丟掉」**
(`exp5/scripts/debug_e2b_empty.py`)。答案很乾脆:

> E2B 在 `T2_30s` 上**生成了 1 個 token,就是 `<eos>`**。
> `skip_special_tokens=True` 是空字串,`parse_response()` 之後也是空字串。
> 同一個視窗給 E4B 是 75 個 token 的可讀逐字稿。

**不是解析 bug。但診斷同時翻出一個更大的問題:**
重跑 `T2_155s` 得到 `<eos>`,而正式跑那次它產出了 119 字——同一個模型、
同一份輸入、不同結果。查 `generation_config.json`,三個 Gemma **全部**是:

```json
{"do_sample": true, "temperature": 1.0, "top_k": 64, "top_p": 0.95}
```

**本專案所有 Gemma 數字都是在溫度 1.0 的隨機取樣下量的,而且都只跑一次。**
這件事先前完全沒被記錄(見侷限 16n)。

#### 貪婪解碼對照(§4 C-ter,規則先寫死)

同樣 8 個視窗,E2B 與 E4B 各用 `do_sample=False` 重跑:

| arm | CER 平均 | 長度比 | 空輸出 |
|---|---|---|---|
| E4B(取樣) | 0.312 | 1.18 | 0/8 |
| **E4B(貪婪)** | **0.295** | 1.17 | 0/8 |
| E2B(取樣) | 0.894 | 0.35 | 6/8 |
| **E2B(貪婪)** | **1.000** | **0.00** | **8/8** |

**兩個結論,都對應 §4 C-ter 預先寫死的表:**

1. **「E2B 仍大量空輸出 → 解釋 (a) 成立」。** 而且比取樣時更徹底:貪婪下
   **8/8 全空**。`<eos>` 是它的 **argmax 第一個 token**——
   溫度 1.0 的取樣是它唯一會開口的原因。**E2B 在這批語料上是真的拒絕轉寫。**
2. **E4B 的變動是 −0.017(逐視窗最大 0.041),全部 < 0.05 門檻**
   → 不觸發「所有 Gemma 數字都要重新量」那一條。E4B 的數字穩定。

#### 判讀(§4 C-bis)

規則第三列:**「E2B < E4B(明顯更差)→ 不是單調的,E4B 是甜蜜點」。**

> **「越小越穩」是錯的。** 12B 吐太多、E2B 不吐、E4B 剛好——
> 這個家族裡有一個甜蜜點,而不是一條單調曲線。
> 侷限 16k(「不能說小模型一定比較好」)**現在有實際反證了**,不再只是謹慎措辭。

**「參數量不是能力的代理指標」因此在兩個方向上都成立**:往大(12B)壞,
往小(E2B)也壞。選型只能逐個型號實測。

#### 基準線也對得上

E2B 的 selftest(模型卡官方英文樣本 `journal1.wav`)**本來就已經退步了**:

| 模型 | 官方樣本輸出 |
|---|---|
| 12B / E4B | `Woke up early today feeling refreshed. The morning light was beautiful and I enjoyed a nice cup of coffee.` — 完美 |
| **E2B** | `A good call today feeling really fresh the morning light was superb and i enjoyed a nice cup of coffee` |

`Woke up early` → `A good call`、`beautiful` → `superb`、標點全失、`i` 沒大寫。
**鐵律 7 那條基準線的價值又一次體現**:E2B 的低分不能全歸咎於語料契合度,
它在模型卡自己的樣本上就不夠好了——而 12B 與 E4B 在同一個檔上都是完美的。

### 3F.2j 貪婪對照:12B 的跳針不是取樣造成的,而且取樣還幫過它(handoff-v9 J)

**這是 v9 裡風險最高的一格。** §3F.2b/2g 的整個故事是「12B 退化生成」,
但那些數字全是在 `temperature: 1.0` 的隨機取樣下量的(侷限 16n),
**從沒驗過貪婪解碼**。如果跳針在貪婪下消失,那「12B 不能聽」就是被取樣害的,
而這個結論已經寫進 README、`stt-matrix.md`、CLAUDE.md 鐵律 9 與本報告四處。

判讀門檻寫在 handoff-v9 §3 J,**在跑之前就寫死**。結果:

| arm(純中文 20 秒視窗) | CER 平均 | CER 最差 | 長度比 |
|---|---|---|---|
| Gemma 4 12B(取樣) | 2.231 | 6.833 | 2.21 |
| **Gemma 4 12B(貪婪)** | **3.518** | **8.333** | **3.48** |

**貪婪更糟,不是更好。** 依 §3 J 第一列(CER 仍 > 1.5 且長度比仍 > 1.8)
→ **退化生成是模型性質,現有結論全部成立,四份文件一個字都不用改。**

而且結論比原本**更強**:重複迴圈在貪婪解碼下被放大是這類失效的典型行為
(取樣會隨機跳出迴圈,貪婪不會)。**先前那個 2.231 其實是取樣「幫過」12B
之後的成績**——它真正的、可重現的表現是 3.518。

#### E4B 的方向相反:取樣讓它變差

| exp5(158 實例/條件) | 取樣 | **貪婪** | Δ |
|---|---|---|---|
| M0 乾淨 | 0.741 | **0.791** | **+0.051** |
| M3 混響+12dB 交談 | 0.627 | **0.665** | **+0.038** |

依 §3 J 第二張表:M0 的 **+0.051 ≥ 0.05** 門檻
→ **「exp5 主表的 E4B 數字要標成單次取樣的點估計,並補跑 M3」**。
M3 已依規則補跑(+0.038),**兩個條件同方向**。

> **貪婪下的 E4B 是 0.791 / 0.665(平均 0.728),高於 Speechmatics batch 的 0.699。**
> 也就是說 §3F.2g 說的「與 SM batch 同級」在貪婪設定下其實是**略勝**。

⚠️ 0.051 只比門檻高 0.001。**沒有因為它接近門檻就當作沒過**——
規則怎麼寫就怎麼判(與 §2.1c 的 N3、§3F.2i 的長度比盲點同樣處理)。

#### 這一格改了什麼

1. **12B 的結論不用改**,但要補一句「貪婪下更糟」,免得有人以為換解碼就能救。
2. **E4B 的 exp5 數字改用貪婪那組當主數字**(可重現),取樣那組保留為對照。
3. 侷限 16n 從「未量測」改成「**已量測:12B 與 E4B 都做了,方向相反**」。

### 3F.2h 日文那格補滿:0.323 站得住,而切塊的代價 ≈ 0(handoff-v8 §2 E)

### 3F.3 結論與適用邊界

**第一跳(聽):看型號,不要看廠牌。**

- **12B:不要用。** 0.028 vs Breeze 0.845,而且慢 19 倍、貴 5 倍。
  它的失效模式是**退化生成**(重複迴圈,輸出 2.2 倍長),不是聽不懂(§3F.2g)。
- **E4B:中文可用,日文不可用。** exp5 0.741/0.627(平均 0.684,與
  Speechmatics batch 0.699 同級)、純中文 CER 0.312、輸出長度比 1.04。
  但日文只有 0.400,離 SM+詞表的 0.969 還很遠。
- **kikemu 本業(日文即時)兩個都不用**——即時這個需求先擋掉自架這條路,
  日文那格又沒過門檻。E4B 的價值在**中文、非即時、資料不能出境**的場景。

**第二跳(譯):kikemu 不換,但非即時線有價值。**
即時字幕的瓶頸是延遲不是成本(§5 已量過),Gemma 慢 3 倍買不回省下的 $0.107/hr。
但事後逐字稿沒有延遲壓力,換成 Gemma 4 就是同品質、1/22 成本。

**「全地端聽譯鏈」= Breeze 聽 + Gemma 4 譯 —— 已端到端驗證,而且贏過雲端兩跳,
但只在中文上。**(原本標未驗證,handoff-v8 §1 F 接起來了,見 §3F.4。)
驗證語料是中英夾雜的中文 podcast;**日文那一跳是壞的**——§2.1c 量到 Breeze 在
日文只有 0.415,對 SM+詞表的 0.791 輸 −0.376。**這條鏈不能拿去做日文導覽。**

### 3F.4 全地端聽譯鏈:端到端驗證(handoff-v8 §1 F)

報告先前說「全地端鏈 = Breeze 聽 + Gemma 4 譯」但標**未驗證**——兩端各自
的數字都有,中間從沒接過。這一格把它接起來:**不重跑聽的那一跳**,
直接吃既有的 exp5 轉寫,所以不用 GPU,成本只有譯那跳的 API 費。

> **先講適用邊界,免得表被單獨引用:這一格全部是中文語料(exp5 中英夾雜 podcast)。
> 「全地端鏈可用」這個結論只對中文成立。** 同一個 Breeze 在日文上只有 0.415
> (§2.1c),鏈的第一跳就垮了——**kikemu 的日文導覽本業用不到這條鏈**,
> 它服務的是「資料不能出境的中文事後逐字稿」。

三條鏈同料(輸入音檔完全相同,只有引擎組合不同,譯的 prompt 都是凍結的
`INTERPRETER_SYSTEM`、都 `thinkingLevel: minimal`):

| 鏈 | 英文術語在譯文中存活 | 台灣用語誤用 | 簡體殘留 |
|---|---|---|---|
| Breeze → **gemini-3.5-flash** | **0.795** | 0 | 0 |
| **Breeze → gemma-4-26b-a4b-it**(全地端) | **0.717** | **0** | **0** |
| Speechmatics → gemini-3.5-flash(現行產線形狀) | 0.626 | 0 | 0 |

#### 判讀(handoff-v8 §4,規則先寫死)

> 三個指標都不比「SM + Gemini」差超過 10% → 全地端鏈**成立**

**成立,而且不是勉強成立:全地端鏈 0.717 比雲端兩跳的 0.626 高 +0.091。**
台灣用語誤用與簡體殘留都是 0,譯文沒有跳針(最長重複片段 0 字)。

#### 拆成兩跳看,結論更有用

| 換掉哪一跳 | Δ |
|---|---|
| **聽**:SM → Breeze(譯都用 Gemini) | 0.626 → 0.795 = **+0.169** |
| **譯**:Gemini → Gemma 4(聽都用 Breeze) | 0.795 → 0.717 = **−0.078** |

**Breeze 在聽的那跳賺到的,遠多於 Gemma 在譯的那跳賠掉的。**
所以全地端鏈能贏,主力是 ASR 換得好,不是翻譯換得好——
這也解釋了為什麼 §3E.2 量到 Breeze 的術語召回(0.845)遠高於 SM(0.699)。

譯文品質抽看沒有問題:

> 主要是工業園區,蘇州的工業園區是那種完全照新加坡的建築風格……
> 所以你剛才提到在做這個 Search Engine,對,那時候加入了 Microsoft Search
> Engine Team,當時做的差不多就是 Bing。我在非常 Core 的團隊……

英文原樣保留、台灣正體、語序自然。

#### 但這條鏈**不適用於 kikemu**

它是**非即時**的:Breeze 在 T4 上 2.9~4.6× 實時、Gemma 26B 譯一段要 20~22 秒
(Gemini 是 4.6~5.3 秒)。kikemu 要的是即時字幕,這條鏈給不了。
它適用的是**資料不能出境的事後逐字稿**——那正是 `stt-matrix.md` §6 那一格。

**而且語言限定仍然成立**:這一格是中英夾雜語料。§2.1c 量到 Breeze 在**日文**
只有 0.415(SM+詞表 0.791),所以「全地端鏈」目前只驗證過中文場景。

### 3F.4b E4B 當耳朵的全地端鏈:更差,而且壞在意料之外的地方(handoff-v9 G)

§3F.4 驗過的全地端鏈第一跳是 **Breeze**。v8 之後 E4B 才有資格當第一跳,
但從沒接過。這一格把五條鏈放在同一批音檔上比(譯的 prompt 都是凍結的
`INTERPRETER_SYSTEM`、都 `thinkingLevel: minimal`):

| 鏈 | 英文術語存活 | 台灣用語誤用 | 簡體殘留 |
|---|---|---|---|
| Breeze → gemini-3.5-flash | **0.795** | 0 | 0 |
| **Breeze → gemma-4-26b(全地端)** | **0.717** | **0** | **0** |
| Speechmatics → gemini-3.5-flash | 0.626 | 0 | 0 |
| Gemma 4 E4B → gemini-3.5-flash | 0.615 | 1 | 0 |
| **Gemma 4 E4B → gemma-4-26b(純 Gemma)** | **0.518** | **14** | 0 |

#### 判讀(handoff-v9 §3 G,規則先寫死)

**第一張表:** `chain_e4b_gemma` = **0.518 < 0.65** → 第三列:
**「E4B 的召回劣勢會傳到下游 → 全地端鏈的耳朵指定 Breeze,E4B 只當備案。」**

**第二張表(獨立判準,第二跳固定 Gemini,只換耳朵):**
0.795 − 0.615 = **0.180**,而兩者的 ASR 術語召回差是 0.845 − 0.684 = **0.161**。
同量級 → **召回差原樣傳到下游,ASR 召回是好的下游代理指標。**
(這對選型有用:比較地端 ASR 時不必每次都把整條鏈接起來。)

#### 但真正值得記的是那個「14」

**這是本專案所有鏈裡第一次出現非零的台灣用語誤用。** 全部是同一個詞:**「數據」**
(台灣用「資料」)。逐檔追下去,機制很乾淨:

| `T1__M0` | 轉寫裡的拉丁 `data` | 轉寫裡的「數據」 | 譯文裡的 `data` | 譯文裡的「數據」 |
|---|---|---|---|---|
| **Breeze** → gemma-26b | 4 | 0 | **2** | **0** |
| **Gemma 4 E4B** → gemma-26b | 4 | 0 | **0** | **8** |

**同一個譯者、同一份凍結 prompt、轉寫裡同樣有 4 個拉丁 `data`,
結果一邊留著、一邊全部譯成中國用語。** 唯一的差別是轉寫的**形式**:

- Breeze 的輸出**沒有標點、沒有分句**,是一長串字
- E4B 的輸出**有標點、句子完整、讀起來像寫好的文章**

> ~~**看起來越像成品的轉寫,下游 LLM 越敢改它。**~~
> **這個機制推測後來被自己的實驗推翻了,見 §3F.4c。** 保留原文是因為
> 它決定了後續怎麼設計驗證——結論怎麼被推翻的過程比結論本身有用。

這對 kikemu 是**直接相關的風險**,因為台灣正體用語是產品的硬需求(鐵律 3),
而這條路徑上沒有任何一層會攔下「數據」——第一跳沒錯、prompt 沒錯,
是兩跳的**交互作用**產生的。**這一句仍然成立**,被推翻的只是「為什麼」。

### 3F.4c 那個機制推測是錯的:形式不是主因(handoff-v9 L / M)

§3F.4b 推測「轉寫看起來越像成品,下游越敢改它」。侷限 16p 標明那不是單變因
對照。這一格把形式單獨拆出來驗——**只動形式,一個字元都不改**,
而且**全部是機械操作、不經過任何模型**(用 LLM 加標點會連帶改寫用詞,
那就又多一個混淆變因)。變體由 `exp5/scripts/make_form_variants.py` 產生,
每個都帶一條機器證明:`strip(輸出) == strip(來源)`。

第二跳全部固定 `gemma-4-26b-a4b-it` + 凍結的 `INTERPRETER_SYSTEM`:

| 轉寫來源 | 形式操作 | 英文術語存活 | **「數據」次數** |
|---|---|---|---|
| **Breeze** | 原樣(無標點、有空格) | 0.717 | **0** |
| **Breeze** | **+ 標點**(依自身 segment 邊界) | 0.765 | **0** |
| **Breeze** | **− 空格** | 0.693 | **0** |
| **Gemma 4 E4B** | 原樣(有標點、無空格) | 0.518 | **14** |
| **Gemma 4 E4B** | **− 標點** | 0.500 | **11** |
| **Gemma 4 E4B** | **+ 空格**(拉丁詞兩側) | 0.524 | **16** |

#### 判讀(handoff-v9 §4b / §4c,兩次都在跑之前寫死)

**L(標點):** 加標點沒讓 Breeze 出現「數據」,去標點也沒讓 E4B 降下來
→ 第三列:**標點不是主因。**

**M(空格):** 去空格沒讓 Breeze 出現「數據」(仍是 0),
加空格也沒讓 E4B 降低(14 → **16**,方向還相反)
→ 第三列:**空格也不是主因。**

**合起來看,結論很乾脆:**

> **同一個來源的三種形式,結果幾乎不動;不同來源之間差了一個量級。**
> Breeze 的三種形式全部是 0 次「數據」、英文存活 0.693~0.765;
> E4B 的三種形式全部是 11~16 次、存活 0.500~0.524。
> **兩條帶完全不重疊,而形式在帶內只造成 ≤ 0.05 的擾動。**

**所以 §3F.4b 的機制推測(形式)是錯的,已在該節劃掉。
差異來自轉寫的內容本身,不是它長什麼樣子。**

#### 到此為止,不再猜第三個

handoff-v9 §4c 的規則裡先寫死了一條自我約束:
**「空格與標點都排除的話,不要再提第三個猜測。」**

照辦。目前能講的只有:**已排除形式類的兩個候選(標點、空格),
真正的驅動因素未知。** 它不是召回差(兩份轉寫的拉丁 `data` 出現次數相同)、
不是 prompt(凍結且相同)、不是譯的模型(相同)。
**要再往下需要有語言學訓練的人看轉寫,不是再跑一輪 API。**

#### 對產品建議的影響

- **中文全地端聽譯鏈的耳朵維持 Breeze**,E4B 不取代它。
- 但 §3F.2g 說的「E4B 中文可用」**沒有被推翻**——那講的是 ASR 那一跳,
  它仍與 Speechmatics batch 同級。**可用不等於在鏈裡比較好。**
- 若要用 E4B 當耳朵,第二跳的 prompt 要另外加「保留英文原樣」的指示並重測。
  本專案**沒有做**——凍結的 prompt 不能改(鐵律 3)。

### 3F.5 侷限

1. **n = 6 段、67 個專名、單一條件(N0)**,沒有 bootstrap CI。這是快篩不是定論。
2. **沒有做 adequacy 盲評面板**(exp1 對第二跳做過,這裡沒有)。
   「專名保留 / 台灣用語 / 簡體」三個是自動指標,量不到譯文的流暢度與語用。

## 5. 成本:選 SM 的理由不是便宜

> **2026-08-14 更正**:本節初版把 gemini-3.5-flash 的文字費率抄成
> $0.30/M in、$2.50/M out——**那是 flash-lite 的價**,3.5-flash 是
> **$1.50/M in、$9.00/M out**(官方 pricing 頁,2026-08-14 核實),低估 3.6 倍。
> token 數本身沒錯(當時記的 6.6 萬「output」其實 = 7,123 output + 59,305 **thoughts**,
> 已含思考;thinking token 以輸出價計費)。下表為更正後的數字,並加上關掉 thinking 的一列。

每小時音訊的 API 成本(SM $0.24/hr 與 Gemini Live 音訊輸入 $3/1M 為 handoff §8 提供的費率;
gemini-3.5-flash 以 $1.50/M in、$9.00/M out 計):

| 路線 | 聽 | 譯 | 合計 |
|---|---|---|---|
| SM + 詞表 + Gemini 譯(**實驗當時,thinking 預設開**) | ~$0.24 | ~$0.84 | **~$1.08** |
| SM + 詞表 + Gemini 譯(**產品現況,thinkingLevel:minimal**) | ~$0.24 | ~$0.11 | **~$0.35** |
| Gemini Live 一路(一跳) | 實測 75k audio tokens/hr × $3/1M ≈ $0.22 | 同一跳 | **~$0.22 +音訊輸出** |

- **翻譯那一跳的錢有 87% 是在買思考**:0.73 小時音訊燒掉 11,821 prompt +
  7,123 output + **59,305 thoughts**(thoughts/output = 8.3×)。關掉思考後
  這一跳從 $0.84 掉到 $0.11/hr,而三句抽樣人工比對譯文品質無退化
- 產品端比實驗更吃虧:實驗是整段翻譯(思考前導攤在長文上),產品是**逐句**呼叫,
  同一組 prompt 單句實測 thoughts/output 高達 **29×** —— 8.3× 是地板不是估計
- Gemini Live 的音訊輸出 token 在 usage 回報中不完整,總數會再高一些
- **詞表本身極便宜**:exp1 三個領域自動生成共 66,310 prompt + 33,912 output tokens
  ≈ $0.41,即 **$0.14/景點、一次性**、可重複使用、零延遲代價
- Speechmatics 端無額外費用:`additional_vocab` 隨 session config 送出,
  job 記錄未見附加計費項目(僅以 API 回應觀察,未核對帳單)

**結論:選 SM 路線是為了抗噪與即時性;關掉 thinking 之後,成本($0.35/hr)
與一體式($0.22/hr +音訊輸出)已是同一數量級,「貴一截」的說法不再成立。
但這仍不是「又便宜又好用」——差距來自兩跳架構本身,對外說明要講得出這個數字。**

> 牌價會變(3.6/3.7-flash 目前促銷 $0.75/$3.75,2027-01-01 漲回),
> 成本表一律標查價日期與模型級別;抄價前先確認是 flash 還是 flash-lite。

兩個實驗全部支出 < $7,主要成本是真實速度推流的 wall-clock(約 5 小時)。
