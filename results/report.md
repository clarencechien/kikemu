# kikemu 聽譯引擎評測報告

兩個實驗、一份結論。

- **exp1 — 日文導覽解說**:自訂詞表值不值得成為產品核心?(原 `handoff.md`)
- **exp2 — 中英夾雜技術演講**:同一套詞表機制在語碼混合場景是否同樣有效?(原 `handoff-v2.md`)

原始資料:`results/raw/`(exp1)、`exp2/results/raw/`(exp2)。腳本:`scripts/`、`exp2/scripts/`。
選型速查:`results/stt-matrix.md`。

## 0. TL;DR

**兩個實驗合起來的核心判斷:一體式模型只在直接餵訊號的通道可用;
只要音訊經過空氣,就要用專用 ASR。而詞表值不值得做,取決於「引擎缺的是什麼」。**

| | exp1 日文導覽(專名) | exp2 中英夾雜演講(術語) |
|---|---|---|
| 最佳 arm | SM + 地點詞表 | SM `cmn_en` 雙語 pack(+ 投影片詞表) |
| **詞表邊際價值** | **+0.12 ~ +0.19(核心資產)** | +0.03 ~ +0.05(小加分) |
| 真正的槓桿 | 詞表 | **語言 pack(+0.23 ~ +0.29)** |
| 一體式乾淨條件 | 打平(0.836 vs 0.836) | 略勝(0.927 vs 0.833,CI 下緣壓 0) |
| 一體式崩潰點 | 人聲 8dB → 0.030(全滅) | 人聲 12dB → 0.396(半滅) |
| 在地化/不譯規則 | 原版 prompt 已解決 | 原版 prompt 已解決(P1 零增量) |

**三條可以直接用的規則:**

1. **一體式的門檻是「直接餵訊號」,不是「安靜」。** exp1 裡只加室內殘響、
   完全不加噪音,Gemini Live 就從 0.836 掉到 0.552,而 SM+詞表維持 0.836。
   手機桌上收音、講堂後排這種「聽起來還好」的情況已經出局。
2. **詞表投資判準:目標詞彙是「引擎沒見過的」(在地專名、料號)才值得做大;
   「引擎見過但模式不對」(通用英文術語)要先修語言設定,詞表只是小數點。**
3. **選 SM 路線的理由是抗噪與即時性,不是成本。** 見 §5 —— 兩跳架構的
   API 成本大約是一體式的兩倍,這點要如實對內說明。

**產品建議:kikemu 走 SM + 以地點自動生成詞表 + Gemini 翻譯。
只有能保證 line-in 級音源的通道才考慮降級為一體式,且切換須以現場 SNR 偵測把關
(人聲背景 SNR < 約 15dB 一律不可用)。廠區/會議線改用 `cmn_en` 雙語 pack,
詞表退為進階選項。**

## 1. 方法與信度控制

兩個實驗共用同一套 harness:目錄結構、統計處理、判定規則凍結流程一致。

### 1.1 語料

| | exp1 | exp2 |
|---|---|---|
| 來源 | 大阪觀光局「しっとんか大阪」音訊導覽(ON THE TRIP 製作) | 台大李宏毅 ML2021 / 生成式AI導論2024 |
| 選段 | 6 段(東大阪神道 ×2、堺茶道歷史 ×2、池田近代 ×2) | 3 段 × 5 分鐘(Self-attention / GAN / GenAI 導論) |
| 標準答案來源 | 官方頁面旁白全文 + 雙引擎驗證 | 無官方文字,三路轉寫 + 人工裁決 |
| 授權 | 僅私下評測,音檔不入庫不散布 | 同左;課程公開 ≠ 開放授權 |

### 1.2 標準答案:兩個實驗都不用單人聽寫

**exp1 — handoff 警告的三個陷阱全部命中:**

| 陷阱 | 實況 | 處理 |
|---|---|---|
| 頁面文字 ≠ 音檔內容 | 堺系列音檔只唸頁面文字的前 20~33%(節錄版) | 對齊找出實唸子區間,參考文本裁切 |
| 音檔與段落不是 1:1 | 枚岡神社 B-1/B-2 指向同一 mp3,實際只唸 B-1 | 參考文本只取 B-1 |
| 需人工核對逐字吻合 | 旁白會唸段落標題(頁面正文沒有);少數助詞增減 | 見下方協定 |

驗證協定:每段由兩個獨立引擎轉寫(Speechmatics batch、Gemini 3.5 Flash),
與頁面文字三方對齊,殘差逐條人工檢視(`corpus/reference/review.md`)。
規則 R1–R5 寫死在 `scripts/build_reference.py`,先於任何 arm 執行:

- 兩引擎**一致**而頁面**沒有**的插入(語氣詞「御」「の」)→ 採納
- 同音異寫差異(ことはじめ/事始、アメノコヤネノミコト/天児屋根命)→ **保留官方頁面寫法**,
  避免參考文本偏向任一 ASR 的選字習慣

結果:參考文本與兩引擎的 CER 為 SM 0.03~0.21、Gemini 0.04~0.14,
殘差人工檢視確認除標題與少數助詞外無內容性偏離。

**exp2 — 沒有官方文字,人工裁決比重更高:**

三路獨立轉寫(SM batch cmn、gemini-3.5-flash、gemini-3.6-flash),
以兩個 Gemini 的 token 級一致部分為基底,80 個分歧塊逐條檢視,裁決寫入 `overrides.json`。

**記錄在案的偏離:SM-cmn 不參與英文拼寫表決**——它在受測維度上系統性弱勢
(COVID-19 → 「CoffeeNight」、network → 「news」),讓它投票會污染正解。
但它的中文可靠,用於裁決中文區域:

- 「英年早逝」「火影忍者」「爆雷」——三方證據一致後修正
- **關鍵裁決:講者說的是「函式」不是 "function"**。gm35 把 10 處中文「函式」
  英文化成 function,SM 聽到 8 次 函式/函数 佐證。這同時暴露了
  **「用 LLM 做逐字稿會被它的正字法偏好污染」**這個方法論陷阱
- 數字讀法(one-hot 向量「1 0 0 0」)按實際唸法修正

### 1.3 正解清單與判定規則(執行前凍結)

**exp1 — 67 個專有名詞**(神名、人名、社名、神事名、地名、年代)。
Gemini 從已驗證參考文本抽取,程式強制 surface 必須逐字出現;
機械化整理規則寫死(去子字串重複、通用詞停用表、標題拼接假詞過濾)。

**exp2 — 86 個英文術語實例**(S1 26 個 51 次、S2 10 個 20 次、S3 6 個 16 次)。
機械抽取連續拉丁 token,排除純填充詞與數學式唸法。
每個術語另標 no_translate(架構名/專名/縮寫)或 may_translate(一般技術詞)。

**兩套判定規則並列,均寫死:**

- **strict**:與正解逐字相符(exp1 原規則;exp2 為大小寫不敏感完全相符)
- **tolerant**:另接受官方讀音、凍結的標準別寫法(exp1)/連字號空白折疊與凍結變體(exp2)

結論以 tolerant 為主、strict 為 robustness check;兩者排序一致。

### 1.4 詞表來源與洩漏控制

| 實驗 | 詞表 | 來源 | 條數 | 洩漏控制 |
|---|---|---|---|---|
| exp1 | 地點詞典 | 日文維基百科(站點名 + 城市名) | 142~166/域 | **絕不接觸 osaka-info 文章頁**(該頁是逐字稿來源) |
| exp2 | domain | Google ML Glossary 公開頁 | 645 | **絕不接觸投影片與逐字稿** |
| exp2 | slides | 該堂課官方投影片 PDF | 42/81/22 | 與逐字稿重疊是產品場景,非洩漏 |

### 1.5 聲學條件(真實材料,非合成噪音)

RIR 一律取自 MIT IR Survey,以 Schroeder 積分決定性挑選;噪音取自 DEMAND 實錄。
SNR 以**語音活動段 RMS** 計算(50ms 框、能量閘門 10% of max),不含靜音;
亂數種子固定,每步後峰值正規化。

**exp1(導覽場景)** — 6 段 × 5 條件 = 30 檔:

| 代號 | 處理 |
|---|---|
| N0 | 原始 |
| N1 | + RIR(T60 = 0.600s,`h213_SubwayStation`) |
| N2 / N3 | N1 + DEMAND PCAFETER 食堂人聲 @ SNR 15 / 8 dB |
| N4 | 帶通 300–3400Hz + 削波 + RIR(擴音喇叭) |

**exp2(講堂/會議場景)** — 3 段 × 4 條件 = 12 檔:

| 代號 | 處理 |
|---|---|
| M0 | 原始 |
| M1 | + RIR(T60 = 0.721s,`h100_Classroom`) |
| M2 | M1 + DEMAND OOFFICE @ SNR 20 dB |
| M3 | M1 + DEMAND OMEETING 會議交談 @ SNR 12 dB |

exp2 的 RIR 挑選規則加了空間類別約束(限 Classroom):
無限制時的最接近值是浴室——衰減對、空間錯。規則與理由一併記錄。

### 1.6 實驗 arm

**exp1:**

| arm | 聽 | 譯 |
|---|---|---|
| A | Gemini Live(`gemini-3.1-flash-live-preview`) | 同一模型一路到底 |
| C | Speechmatics 即時 WS(ja, enhanced) | Gemini 3.5 Flash |
| C+ | 同 C + `additional_vocab` | 同 C |
| Cb / Cb+ | Speechmatics **batch**(−/+ 詞典) | — |
| D | Deepgram | **未執行**:環境無帳號 |

**exp2:**

| arm | 聽 | 詞表 | 語言模式 |
|---|---|---|---|
| X_cmn / Xsli_cmn | SM 即時 | 無 / slides | cmn 單語 |
| X_bi / Xdom_bi / Xsli_bi | SM 即時 | 無 / domain / slides | `cmn_en` 雙語 |
| G | Gemini Live 一路 | — | — |

全部即時 WS、**1× 真實速度**推流 0.5s PCM chunk,每則 server 訊息帶時戳落檔。
A/G 與 C/X 共用同一份口譯 systemInstruction(`scripts/prompts.py`,凍結)。

**記錄在案的替代:** handoff-v2 指定 `language: multi`;本帳號的即時 multi 模型
(melia-1)回覆 "currently not supported"。Speechmatics 另有專用中英雙語 pack
`cmn_en`,支援 enhanced / max_delay / additional_vocab 全參數,
比 multi 更貼合句內語碼轉換,故雙語 arm 使用 cmn_en。

### 1.7 統計處理

- 配對設計:同一音檔餵給所有 arm
- 差值附 **segment-cluster bootstrap 95% CI**(10,000 次重抽,以段落為重抽單位,
  因同段內結果相關;種子固定)
- 另報 per-item McNemar 配對計數
- exp1 譯文 adequacy:3 模型盲評(見 §7 侷限)

## 2. exp1 結果:日文導覽解說

### 2.1 專有名詞召回率矩陣(tolerant,67 個專名 micro-average)

| arm | N0 | N1 殘響 | N2 人群15dB | N3 人群8dB | N4 擴音 |
|---|---|---|---|---|---|
| A(Gemini Live) | 0.836 | 0.552 | 0.194 | **0.030** | 0.582 |
| C(SM 無詞表) | 0.716 | 0.687 | 0.672 | 0.433 | 0.687 |
| **C+(SM + 詞表)** | **0.836** | **0.836** | **0.806** | **0.627** | **0.851** |

strict 判定排序完全一致(A 0.716/0.478/0.149/0.015/0.537;
C 0.672/0.627/0.612/0.388/0.627;C+ 0.731/0.731/0.702/0.522/0.746)。
以「譯文中出現該專名」交叉檢核,排序亦不變。

### 2.2 詞表的邊際價值:C+ − C(核心數字)

| 條件 | Δ(tolerant) | 95% CI | McNemar(C+獨對 / C獨對) |
|---|---|---|---|
| N0 | **+0.119** | [+0.016, +0.211] | 8 / 0 |
| N1 | **+0.149** | [+0.056, +0.215] | 10 / 0 |
| N2 | **+0.134** | [+0.037, +0.211] | 9 / 0 |
| N3 | **+0.194** | [+0.138, +0.232] | 14 / 1 |
| N4 | **+0.164** | [+0.071, +0.234] | 11 / 0 |

- 所有條件 CI 排除 0,**愈吵價值愈大**
- McNemar 幾乎單向:詞表救回的詞幾乎沒有代價
- 質性例子(hig01 N0):C 寫「石切剣や神社絵馬伝 / 長脛彦 / 馬島での尊」,
  C+ 正確寫出「石切劔箭神社絵馬殿 / 長髄彦 / 可美真手命」

### 2.3 A − C+ 隨噪音的走勢

| 條件 | Δ | 95% CI | McNemar(A獨對 / C+獨對) |
|---|---|---|---|
| N0 | 0.000 | [−0.103, +0.085] | 7 / 7 |
| N1 | −0.284 | [−0.451, −0.085] | 3 / 22 |
| N2 | −0.612 | [−0.727, −0.519] | 1 / 42 |
| N3 | −0.597 | [−0.771, −0.448] | 1 / 41 |
| N4 | −0.269 | [−0.431, −0.090] | 3 / 21 |

**乾淨條件下 A 確實夠好**(與 C+ 統計上無差),但**任何**現實劣化都讓 A 大幅落後。
關鍵風險:**N3 下 A 系統性崩潰**——hig01/ikeda02/ikeda03/sakai05 四段輸出 0~21 字元。
對這四段獨立重跑(`results/raw/A_recheck/`),**崩潰逐檔重現且輸出字元數一致**,
不是抖動。CER 同樣呈現:A 在 N3 平均 0.911(整段丟失),C/C+ 為 0.34/0.32。

### 2.4 詞典覆蓋率:「自動脈絡包」的天花板

Wikipedia-only 詞典對 67 個正解專名的字面覆蓋:hig01 4/16、hig02 4/13、
sakai05 6/7、sakai06 1/6、ikeda02 5/11、ikeda03 4/14。

即便字面覆蓋有限,C+ 仍全面領先——因為長詞條會連帶救回子字串專名,
通用專名引擎本來就會。**以地點為 key 的自動脈絡包可行且有效,
但對在地小眾詞(いとや百貨店、旧池田電報電話局)有真實天花板。**
產品端可用官方頁面補充(本評測為防洩漏刻意排除),覆蓋率會更高。

### 2.5 譯文品質

- **台灣用語命中(視頻/質量/信息/軟件/網絡等):三 arm 全部 0 次;簡體字元 0 個**
- adequacy(3 模型盲評,1~5 分):

| 指標 | 條件 | A | C | C+ |
|---|---|---|---|---|
| adequacy | N0 | 3.61 | 4.50 | **4.71** |
| adequacy | N3 | 1.08 | 2.33 | **2.44** |
| tw_locale | N0 | 4.94 | 5.00 | 4.94 |

**handoff 預期「A 與 C 相同(共用 systemInstruction)」—— 實測不同,原因已查:**
不是 prompt 差異,而是架構差異。A 是邊聽邊譯,譯文較精簡、會漏細節;
C/C+ 是對定稿後的完整逐字稿整段翻譯,資訊保留較完整。
**注意這對 C/C+ 有利**:真實產品中 C 的翻譯也會是增量式,adequacy 會介於兩者之間(見 §7)。

### 2.6 即時 vs 批次:沒有準確度代價

| arm | N0 | N1 | N2 | N3 | N4 |
|---|---|---|---|---|---|
| C(即時,無詞表) | 0.716 | 0.687 | 0.672 | 0.433 | 0.687 |
| Cb(批次,無詞表) | 0.746 | 0.687 | 0.657 | 0.418 | 0.702 |
| C+(即時,有詞表) | 0.836 | 0.836 | 0.806 | 0.627 | 0.851 |
| Cb+(批次,有詞表) | 0.866 | 0.836 | 0.821 | 0.597 | 0.836 |

差距 −0.03 ~ +0.03,CI 全部含 0 或緊貼 0。**不必為了準確度犧牲即時性。**
且詞表價值在批次模式下同樣是 +0.12 ~ +0.18——**詞表補的不是「即時模式的先天不足」,
而是引擎本身不認識這些在地專名。**

batch 每檔中位處理 9~15 秒、必須等整段講完,與現場即時口譯的產品定義互斥;
其價值在離線預處理(預錄導覽稿的字幕生成)。

### 2.7 晶晶體(輸出端)

掃描 90 份譯文,英文分為 gloss(中文詞旁的括號注釋)與 bare(裸露英文):

| arm | latin_gloss | latin_bare | kana 殘留 |
|---|---|---|---|
| A | 1 | 1 | 3 |
| C | 1 | **0** | **0** |
| C+ | 2 | 2 | 5 |

**總共只有 3 處裸露英文,逐一檢視後沒有一處是風格問題。**
「侘寂（Wabi-Sabi）」是合理的羅馬字注釋;C+ 兩處「天兒屋根命 investment」
追查源頭發現 SM 轉寫完全正確,是翻譯 hop 的偶發幻覺注入。

真正的殘留是**日文假名**(C+ 5 處、A 3 處),且**全部發生在 ASR 已聽錯的位置**——
翻譯模型遇到不成詞的假名選擇原樣保留,是正確的降級行為,但仍是可見瑕疵。

## 3B. exp3 結果:快速前處理救不救得了一體式?(handoff-v3)

問題:exp1/exp2 都是音檔直入、零前處理。在模型前串一個因果式、可串流的
快速降噪,Gemini Live 能不能回到自己的 N0 水準(0.836)?
同時做**差異反應檢定**:同樣的前處理餵 SM,檢驗「SM 是否只是在 model 前
串了前處理」假說。

### 3B.1 前處理器與 RTF

| 手法 | 定位 | RTF(實測) |
|---|---|---|
| webrtc(APM NS level 3) | 官方採集端等價物(瀏覽器/OS 內建那套) | 0.001 |
| sg(譜門檻,1s 塊、僅用過去 2s 上下文) | 傳統法代表,因果模擬 | 0.028 |
| blend(0.75·增強+0.25·原始) | 假影感知混合(Iwamoto 2022) | 0.002 |

RNNoise 未測(pyrnnoise 與環境 PyAV 不相容,記錄缺口)。
全部遠低於 0.3 的即時門檻——「快」不是問題,問題在效果。

### 3B.2 結果:兩邊都救不了

**Gemini Live 側:**

| arm | N0 | N1 | N2 | N3 |
|---|---|---|---|---|
| A(不處理) | 0.836 | 0.552 | 0.194 | 0.030 |
| A + webrtc | 0.791 | 0.567 | **0.075** | **0.000** |
| A + sg | — | — | 0.239 | **0.000** |
| (對照)C+ | 0.836 | 0.836 | 0.806 | 0.627 |

**SM 側(batch + 詞表):**

| arm | N0 | N1 | N2 | N3 |
|---|---|---|---|---|
| Cb+(不處理) | 0.866 | 0.836 | 0.821 | 0.597 |
| + webrtc | 0.881 | 0.836 | 0.791 | 0.567 |
| + sg | 0.836 | 0.851 | 0.791 | 0.507 |
| + blend | 0.836 | 0.851 | 0.806 | 0.493 |

### 3B.3 判讀(對照 handoff-v3 §5 預先寫死的判讀表)

1. **A@N3+pp < 0.2 → 快速降噪救不了 babble,維持原架構結論。**
   最有戲的一刻是譜門檻讓四個原本整段放棄的 N3 檔案重新開口
   (ikeda02 輸出 0→237 字元)——**但召回率是 0.000,CER 0.891**:
   模型開口了,講的都不是原文。降噪打破了「VAD 看不見語音」的癱瘓,
   卻救不回底層辨識——因為譜門檻除不掉「頻譜跟前景一樣」的人聲,
   只是把混合訊號變成另一種模型沒見過的訊號
2. **webrtc 在乾淨音源上有假影傷害**(N0 0.836→0.791)——
   假影文獻(CHiME、Iwamoto 2022)的預測應驗;
   任何部署都必須 SNR 門控,不能全程開著(Google 自家 VoiceFilter-Lite 同款設計)
3. **SM+pp − SM ≈ 0 到負**(N3:webrtc −0.03、sg −0.09、blend −0.10)。
   配合 exp1 的「批次 ≈ 即時」證據,**「SM 只是在 endpoint 後串了前處理」
   假說不成立**:它的抗噪是聲學模型內建的(訓練時多條件增強),
   外掛前處理買不到,吵雜下反而扣分
4. blend × N3 依判讀表免跑:兩個基底手法都失敗,線性混合只會朝原始(0.030)靠攏

### 3B.4 結論

**「為什麼官方不做」的答案經實測後成立:**因為在推論端串快速降噪,
對訓練時已見過噪音的模型(SM)是零到負效果,對沒見過的模型(Gemini Live)
救不回正確性、還傷乾淨音源。降噪要嘛做在**採集端物理層**(指向性麥克風、
近講)、要嘛做在**訓練時**(多條件增強),推論前的軟體補救兩頭不討好。

kikemu 的架構結論不變且更穩固:**吵雜場景的解是換引擎(SM),
不是幫一體式模型加前處理。** 手機遠場收音的產品面改善方向是
物理的(麥克風選型、拾音距離),不是 DSP 的。

## 3C. exp4 結果:指向性拾音——Speak2 級夠不夠,還是要領夾麥?(handoff-v4)

方法:把拾音硬體翻譯成 (ΔDRR, ΔSNR) 聲學參數,對既有加噪檔做配對重合成
(RIR 拆直達+早期/晚期,合成器通過 β=1 重建檢核,誤差 ~10⁻⁴):
card 心形1m(+5,+3)、conf Speak2級陣列1.5m(+9,+6)、lav 領夾0.3m(+18,+15)。
**模擬取樂觀上緣(波束理想對準、未建模真機 DSP);「不夠」的結論比「夠」可信。**

### 3C.1 exp1(導覽語料)

| arm | N2 人群15dB | N3 人群8dB |
|---|---|---|
| A 不處理 | 0.194 | 0.030 |
| A + conf(Speak2級) | 0.537 | 0.284 |
| A + lav(領夾) | 0.642 | 0.507 |
| (對照)C+ 不加指向性 | **0.806** | **0.627** |
| 基準:A@N0 / A@N1 | 0.836 / 0.552 | — |

| arm(SM batch+詞表) | N1 | N2 | N3 |
|---|---|---|---|
| 不處理 | 0.836 | 0.821 | 0.597 |
| + card | 0.836 | 0.851 | 0.701 |
| + conf | 0.836 | 0.851 | **0.791** |
| + lav | 0.851 | 0.836 | **0.821** |

### 3C.2 exp2(會議語料,manemu 問題)

| arm | M2 辦公室20dB | M3 會議12dB |
|---|---|---|
| G 不處理 | 0.792 | 0.396 |
| G + conf(Speak2級) | **0.865** | 0.604 |
| (對照)Xsli_bi 不加指向性 | 0.865 | 0.594 |
| 基準:G@M0 / G@M1 | 0.927 / 0.802 | — |

### 3C.3 判讀(對照 handoff-v4 §4 預寫死的判讀表)

1. **Speak2 級救不回一體式(導覽場景)**:A@N3+conf = 0.284 < 0.5 ✗
2. **連領夾麥也只救一半**:A@N3+lav = 0.507 < 0.75 的門檻——
   即使模擬給了 +18dB DRR / +15dB SNR 的樂觀條件,一體式仍到不了可用區。
   殘餘 23dB SNR 的人聲仍讓它掉四成——**一體式對人聲背景的敏感度
   遠超出「改善拾音」能補償的範圍**
3. **最有力的一行對照:SM+詞表「不加任何指向性」(0.627)仍勝過
   A+領夾麥(0.507)。** 架構結論第三度加固
4. **SM 吃得到指向性紅利**(判讀表:C+@N3+conf − C+@N3 = +0.19 ≥ +0.1 ✓):
   conf 0.791、lav 0.821,貼到自己的無噪天花板。**好麥克風的錢應該花在
   SM 這條線上**——與 exp3(外掛 DSP −0.09)成完整對比:
   物理 SNR 改善有效,軟體降噪無效
5. **manemu/Speak2:落在判讀表的中間帶**。G@M3+conf = 0.604
   (「值得」門檻 0.75 ✗、「不必買」門檻 0.6 也未跌破)。
   誠實的讀法:M2(一般會議室)+conf 從 0.792 → 0.865,回到接近乾淨水準,
   **這一段 Speak2 是值得的**;M3(多人交談進行中)只回到 0.604,
   與 SM 打平——會議正熱時一體式仍不舒適。
   **manemu 的近場對話本體(≈M0)不需要 Speak2;
   要在會議室桌面用 manemu,Speak2 讓它在非尖峰時段可用**

### 3C.4 結論

**導覽線(kikemu):指向性能讓 SM 更好,救不了一體式。**
散客遠場的正解維持 SM+詞表;若能讓導覽員戴領夾麥,SM 到 0.82+,
且此時甚至還輪不到考慮一體式(它連領夾都只有 0.507)。

**會議線(manemu):Speak2 級會議麥值得配,但買它是為了「把一般會議室
變成乾淨音源」,不是為了救多人交談尖峰**——尖峰時段仍是 SM 的場子。

**全部為聲學模擬,樂觀上緣。「conf/lav 不夠」的結論可信;
「SM+lav = 0.82」這類正向數字若要作為採購依據,需真機驗證。**

## 3D. exp2 追加 arm:Breeze ASR 25(X-breeze)— Phase A 快篩

**問題**:針對台灣華語與中英夾雜微調的開源模型(Whisper-large-v2 微調,Apache 2.0),
在沒有任何詞表的情況下,英文術語召回能不能贏商用引擎?它沒有 keyterm 機制,
量的是**純模型能力**——exp2 回答了「詞表值多少錢」,這一格回答「模型調校值多少錢」。

跑法見 `notebooks/breeze_asr25.ipynb`(Colab T4,fp16,`chunk_length_s=0` sequential,
模型 revision 釘死)。音檔由 `exp2/scripts/degrade.py` 現場重建並對 SHA256,
與其他 arm 位元相同。

### 結果(tolerant 召回;Phase A = S1-M0 / S1-M3 / S3-M0)

| arm | S1-M0 乾淨 | S1-M3 +交談 12dB | S3-M0 乾淨 | 合計 |
|---|---|---|---|---|
| X_bi(SM 雙語,無詞表) | 0.848 | 0.475 | 0.438 | 0.634 |
| Xsli_bi(SM 雙語 + 投影片詞表) | 0.881 | 0.542 | 0.438 | 0.679 |
| G(Gemini Live 一體式) | 0.898 | 0.424 | 0.938 | 0.694 |
| **X-breeze(無詞表)** | **0.949** | **0.780** | 0.875 | **0.866** |

**三個檔全部領先,而且最大的贏面在最吵的條件**:M3 上 +0.31 對 X_bi、
+0.24 對 Xsli_bi(**贏過配了詞表的 Speechmatics**)、+0.36 對 Gemini Live。

**預先登記的疑慮沒有發生。** 事前擔心「中文訓練資料全為合成語音,真實噪音下會崩」——
沒有崩,它反而是抗噪最好的一個 arm。

### 但它有一個 Whisper 家族的老毛病

M3 的轉寫裡有一段 **`,000,000,000` 重複 167 次**的迴圈(189 字元,三段),
觸發點是講者唸 one-hot vector 的「1 後面很多個 0」。M0 兩個檔都沒有這個問題。

| S1-M3 | TER | CJK 字元比 |
|---|---|---|
| 原始輸出 | 0.380 | 0.81 |
| 收掉重複迴圈後 | **0.261** | 0.92 |
| (對照)X_bi | 0.290 | 0.96 |
| (對照)Xsli_bi | 0.265 | 0.96 |
| (對照)G | 0.807 | 0.89 |

**術語召回不是靠這段垃圾灌出來的**:收掉重複前後,字面命中的術語種數都是 15/26,
完全沒變(重複的內容是數字,不會誤中任何英文術語)。收掉之後 TER 0.261 也是全場最佳。
所以正確的說法是:**轉寫品質很好,但有一個局部、可偵測、可後處理的重複迴圈**——
產品要用它的話,加一個「連續重複 n-gram 就截斷」的後處理即可,這是 Whisper 生態的標準做法。

### `language` 參數:沒有差別(且原因查得出來)

`language=None`(自動偵測)與 `language="zh"` 的輸出**位元完全相同**(三個檔皆是,
耗時不同證明兩趟都真的跑了)。原因在模型的 `generation_config.json`:
`forced_decoder_ids: [[1, None], [2, 50359]]` —— 語言槽是 `None`(留給自動偵測)、
task 固定 transcribe。這批音訊自動偵測本來就判成中文,所以指不指定沒有差。

⚠️ **尚未排除的另一種解釋**:transformers 5.13 可能根本沒把 `generate_kwargs` 的
language 吃進去。要排除很便宜——拿一個檔跑 `language="en"`,輸出若改變就證明參數有效。
Phase B 前補這一槍。

### 這一格改變了 exp2 的結論嗎

改變了一半。exp2 說「中英夾雜的槓桿是語言 pack(+0.23~0.29),詞表只是小加分」——
X-breeze 顯示**還有第三個更大的槓桿:換一個為這個語域微調過的模型**,
它在無詞表的情況下贏過「雙語 pack + 詞表」的組合。

但先別急著改架構,見下面的偏誤警告。

### 🚨 訓練資料污染(不是「疑似偏誤」,是已證實)

查 Breeze ASR 25 的模型卡,訓練資料組成是:

| 來源 | 時數 | 性質 |
|---|---|---|
| ODC Synth | 10,000 hr | 合成中文(FineWeb2 文本 + BreezyVoice TTS)|
| CommonVoice17-EN | 1,738 hr | 真實英文 |
| **NTUML2021** | **11 hr** | **真實中英夾雜** |

**`NTUML2021` = 台大機器學習 2021 = 本評測 S1(自注意力)與 S2(GAN)的來源課程。**
也就是說,**這個模型是在我們的評測語料上微調過的**。這不是「團隊熟悉這個語域」的
軟性偏誤,是直接的訓練/測試污染。(致謝名單裡的李宏毅教授指導,只是同一件事的表面。)

**Phase A 的數字本身就洩漏了這件事**:

| 檔 | 來源課程 | X-breeze | G(Gemini Live) | |
|---|---|---|---|---|
| S1-M0 | **ML2021**(在訓練集內) | **0.949** | 0.898 | Breeze 贏 |
| S3-M0 | 生成式AI導論 2024(不在) | 0.875 | **0.938** | **Breeze 輸** |

在訓練集內的課程大贏、換一門課就輸給一體式——與污染假說一致。
(單點觀察,不是證明:S3 只有一個檔,且兩門課同一位講者、語域相近。)

### 這一格現在能說什麼、不能說什麼

**能說**:
- M3(混響 + 12dB 交談)上 0.780 vs 全部 SM arm 的 0.42~0.54,**抗噪優勢的量級
  大到不像單純的記憶**——記住逐字內容不會讓模型在噪音下更會聽,
  這比較像 Whisper-large-v2 本身的聲學穩健性 + 中文微調的加成。
- 事前登記的「合成訓練資料在真實噪音下會崩」**沒有發生**。
- 開源、Apache 2.0、可地端,對有資料落地需求的場景是真實選項。

**不能說**:
- ❌「Breeze 在中英夾雜上贏過 Speechmatics」——S1/S2 的數字沒有資格支持這句話。
- ❌ 任何把 S1、S2 的召回率當作通用能力指標的推論。

**S3 是目前唯一乾淨的觀察**,而它的結論是「輸給 Gemini Live、贏過所有 SM arm」。

### 下一步的優先順序(已因污染而改變)

1. **領域外語料**(最高優先,見 handoff-v5 §7)。沒有它,這個 arm 的主結論不成立。
   S1/S2 已經沒有救——它們在訓練集裡,再怎麼跑統計都沒用。
2. Phase B 的完整矩陣**只對 S3 有意義**;S1/S2 跑完只能當作「污染條件下的上界」。
3. 若要留 S1/S2 的數字,必須在每一處標註「模型在此語料上訓練過」。

### 樣本規模

Phase A 只有 3 個檔(S1 兩條件 + S3 一條件,合計 134 個術語實例),
**沒有跑 bootstrap CI,也沒有配對檢定**——這是快篩不是定論。

> **後續:§3E(exp5)已用領域外語料回答了這一節留下的問題。**
> 結論是「優勢有真實成分,但被污染放大約 2~3 倍;真正站得住的是抗噪那一格」。
> 上面「下一步」的第 1 項(領域外語料)已完成;第 2、3 項因此不再需要——
> S1/S2 的 Phase B 只會產出污染條件下的上界,沒有決策價值。

## 3E. exp5 結果:Breeze 的優勢出了訓練領域還在嗎?(handoff-v6)

**問題**:§3D 證實 Breeze ASR 25 的訓練資料含 `NTUML2021`,也就是 exp2 的 S1/S2

### 3E.4 判讀(對照 handoff-v6 §5 預先寫死的判讀表)

規則設 Δ = Breeze 減 SM 的 tolerant 召回:

| 預先寫死的門檻 | 實測 |
|---|---|
| ≥ +0.15 且 M3 仍領先 → 優勢可推廣 | |
| **+0.05 ~ +0.15 → 有優勢但被污染放大** | **Δ = +0.146 ← 落這格** |
| ≈ 0 或為負 → 領先主要來自污染 | |

而且這個 +0.146 **還是偏高的估計**:規則寫的基準是 `X_bi`(realtime),exp5 的 SM
主要跑 batch;在唯一兩者都跑過的檔(T1__M0)上 realtime 比 batch **高 0.057**。
換算成 realtime 基準,Δ 大約是 **+0.09**,更深入中間那一格。

對照 Phase A(污染語料)的 Δ = **+0.281**:**去掉污染後優勢掉到約一半,
換成 realtime 基準則掉到約三分之一。**

**結論:Phase A 的領先有真實成分,但被訓練污染放大了大約 2~3 倍。
Breeze 是「領域內強、領域外小贏」,不足以改變 kikemu 的架構選擇。**

### 3E.5 但 M3 那一格是真的

handoff-v6 §5 特別交代 M3 要單獨看,理由是「記住逐字內容不會讓模型在噪音下更會聽」。
實測站得住:

- Breeze 在 M3 上贏 SM batch **+0.165**,贏 Gemini Live **+0.259**(CI 都不含 0)。
- Gemini Live 從 M0 的 0.930 掉到 M3 的 **0.551**(掉 0.379);
  Breeze 只從 0.880 掉到 0.810(**掉 0.070**)。
- TER 同向:Breeze 0.161 平均,SM batch 0.202,Gemini Live 0.313。

**但不要把這讀成「Breeze 抗噪最強」——它不是。** M3 的全 arm 排名:

| arm | M3 | M0→M3 掉幅 |
|---|---|---|
| Gemini 3.7-flash batch ※ | **0.880** | 0.082 |
| Gemini 3.5-flash batch ※ | 0.816 | 0.171 |
| Breeze ASR 25 | 0.810 | **0.070** |
| Speechmatics batch | 0.646 | 0.107 |
| Gemini 3.1 Live | 0.551 | 0.379 |

Breeze 在 M3 贏的是 **SM 與 Gemini Live**;Gemini `generateContent` 與它打平(3.5)
或贏它(3.7)。那兩格有主場優勢(§3E.7),但 3.7-flash **沒有參與造參考**,
所以 0.880 不能當成純粹的自我比對打掉。Breeze 唯一穩坐第一的是**掉幅**,
而 3.7-flash 的 0.082 也很接近。

**所以 Breeze 不可替代的地方不是抗噪排名,而是「唯一能地端跑,而且抗噪夠好」**
(Apache 2.0)。另外兩家都是雲端 API,音訊一定要送出去。

失效模式指向它為什麼耐吵:Breeze 的 F1(整段漏聽)只有 12,SM batch 是 37;
但 Breeze 的 F2(聽成別的詞)有 36,接近 SM 的 37——**它很少放棄,但常聽錯**。

### 3E.5b 即時與非即時的最佳解剛好相反

同一家、同一批音檔,Live 版在噪音下崩得最兇:

| | M0 | M3 |
|---|---|---|
| Gemini **Live**(3.1-flash-live-preview) | **0.930**(即時裡最好) | **0.551**(全場最差) |
| Gemini **batch**(3.5 / 3.7-flash) | 0.987 / 0.962 | 0.816 / 0.880 |

**注意 3.5-flash 沒有 Live 端點**,Live 與 batch 是不同模型、不同 API,不能合稱。

實務選型:

| 情境 | 選誰 | 理由 |
|---|---|---|
| 即時 + 安靜 | Gemini Live | M0 0.930 |
| 即時 + 吵(**kikemu 的情況**) | **Speechmatics** | M3 0.646 vs Live 0.551 |
| 不需即時、要快要便宜 | Gemini 3.5-flash `generateContent` | 28.8× 實時、$0.26/hr;無 timestamp / diarization |
| 資料不能出境 / 要地端 | **Breeze ASR 25** | 唯一能地端跑,且 M3 0.810 |

這一格**不改 kikemu 的架構**:產品要即時、導覽現場會吵 → 仍然是 SM。

### 3E.6 順帶量到的:不需要即時時,Gemini 有多快多省

arm `G` 用 Live API,按 1× 實時推流,5 分鐘音檔就要跑 5 分鐘——那是**即時的代價,
不是 Gemini 的速度上限**。若情境不需要即時也不需要 timestamp,該比的是
`generateContent`:

| | 速度(5 分鐘音檔) | in / out+thoughts tokens per hr | 成本/hr |
|---|---|---|---|
| Gemini 3.5-flash `minimal` | **8–16s(28.8× 實時)** | 90.6k / 13.9k | **$0.26** |
| Gemini 3.7-flash `low` | 12–17s(21.0× 實時) | 90.6k / **284k** | **$2.69** |
| Speechmatics batch | 25–51s(6–12× 實時) | — | $0.24(牌價) |
| Gemini 3.1 Live | 300s(1×) | — | ~$0.22 +音訊輸出 |
| Breeze(本次 CPU/fp32) | 2089–2253s | — | 電費 |

(價格 $1.50/M in、$9.00/M out、gemini-3.x-flash 級,2026-08-14 核實;
SM $0.24/hr 為 handoff §8 費率。原始檔 `exp5/results/raw/Gbat*/`。)

兩條要記住的:

1. **`gemini-3.7-flash` 不支援 `thinkingLevel: "minimal"`**,送出去 400
   `Thinking level MINIMAL is not supported for this model`。退到 `low` 之後
   thoughts/output = **18.7×**,成本跳 10 倍。鐵律 4 在音訊轉寫上同樣成立,
   而且「換更新的模型」不必然更省。詳見 `docs/gemini-api-lessons.md`。
2. 這條路**沒有 timestamp、沒有 diarization、不能串流**,所以對 kikemu 本身不適用
   (產品要求就是即時字幕)。它適用的是「離線把錄音轉成文字」那類用途。

**未驗證**:LLM 轉寫會把話「修順」。3.5-flash 的輸出比 SM batch 長約 26% 且更通順,
那多出來的部分是補完還是補出來的,**沒有做人工聽核**,不要當成準確度的證據。

### 3E.7 這一節的已知偏差(三條,都會影響怎麼讀上面的表)

1. **參考轉寫是 Gemini 產生的。** `exp5/scripts/transcribe_ref.py` 用
   `gemini-3.5-flash` 為預設(gm35)、`gemini-3.6-flash` 查一致性、SM 只是第三意見
   **沒有投票權**。所以 **Gemini 系全體有主場優勢,SM 與 Breeze 是拿對手的轉寫
   當標準答案在被評分。**
   - 反證一:arm `G`(Gemini 3.1 Live)也只有 0.741,優勢並非壓倒性。
   - 反證二:另跑**沒參與造參考**的 `gemini-3.7-flash` 得 0.921,與 3.5 的 0.902
     幾乎一致 → 不是單純的自我比對。
   - 但 **Breeze 與 SM 之間的比較不受這條影響**(兩者都是外人),
     3E.3 第一列與 3E.4 的判讀因此仍然成立。
2. **Breeze 這次跑在 CPU/fp32,不是 notebook 的 T4/fp16。** 這台機器沒有 GPU。
   model revision、`chunk_length_s=0`、`return_timestamps`、`language_arg=None`
   全部相同,只有 device/dtype 不同,並寫進每筆結果的 meta
   (`exp5/scripts/run_breeze_cpu.py`)。數值差異未量測。
3. **SM 用 batch 不是 realtime**,原因是這個帳號的 realtime 併發上限是 1,
   殘留 session 會把整條路堵死。方向已知(batch 低估 SM 約 0.057),
   3E.4 已據此調整結論。

### 3E.8 樣本規模

3 段 × 2 條件 = 6 檔 × 4 個主要 arm,128 個術語實例。
bootstrap 只有 3 個 cluster,CI 寬。**這足以推翻「優勢可推廣」,
不足以精確估計優勢有多大。**

## 5. 成本:選 SM 的理由不是便宜

> **2026-08-14 更正**:本節初版把 gemini-3.5-flash 的文字費率抄成
> $0.30/M in、$2.50/M out——**那是 flash-lite 的價**,3.5-flash 是
> **$1.50/M in、$9.00/M out**(官方 pricing 頁,2026-08-14 核實),低估 3.6 倍。
> token 數本身沒錯(當時記的 6.6 萬「output」其實 = 7,123 output + 59,305 **thoughts**,
> 已含思考;thinking token 以輸出價計費)。下表為更正後的數字,並加上關掉 thinking 的一列。

每小時音訊的 API 成本(SM $0.24/hr 與 Gemini Live 音訊輸入 $3/1M 為 handoff §8 提供的費率;
gemini-3.5-flash 以 $1.50/M in、$9.00/M out 計):

| 路線 | 聽 | 譯 | 合計 |
|---|---|---|---|
| SM + 詞表 + Gemini 譯(**實驗當時,thinking 預設開**) | ~$0.24 | ~$0.84 | **~$1.08** |
| SM + 詞表 + Gemini 譯(**產品現況,thinkingLevel:minimal**) | ~$0.24 | ~$0.11 | **~$0.35** |
| Gemini Live 一路(一跳) | 實測 75k audio tokens/hr × $3/1M ≈ $0.22 | 同一跳 | **~$0.22 +音訊輸出** |

- **翻譯那一跳的錢有 87% 是在買思考**:0.73 小時音訊燒掉 11,821 prompt +
  7,123 output + **59,305 thoughts**(thoughts/output = 8.3×)。關掉思考後
  這一跳從 $0.84 掉到 $0.11/hr,而三句抽樣人工比對譯文品質無退化
- 產品端比實驗更吃虧:實驗是整段翻譯(思考前導攤在長文上),產品是**逐句**呼叫,
  同一組 prompt 單句實測 thoughts/output 高達 **29×** —— 8.3× 是地板不是估計
- Gemini Live 的音訊輸出 token 在 usage 回報中不完整,總數會再高一些
- **詞表本身極便宜**:exp1 三個領域自動生成共 66,310 prompt + 33,912 output tokens
  ≈ $0.41,即 **$0.14/景點、一次性**、可重複使用、零延遲代價
- Speechmatics 端無額外費用:`additional_vocab` 隨 session config 送出,
  job 記錄未見附加計費項目(僅以 API 回應觀察,未核對帳單)

**結論:選 SM 路線是為了抗噪與即時性;關掉 thinking 之後,成本($0.35/hr)
與一體式($0.22/hr +音訊輸出)已是同一數量級,「貴一截」的說法不再成立。
但這仍不是「又便宜又好用」——差距來自兩跳架構本身,對外說明要講得出這個數字。**

> 牌價會變(3.6/3.7-flash 目前促銷 $0.75/$3.75,2027-01-01 漲回),
> 成本表一律標查價日期與模型級別;抄價前先確認是 flash 還是 flash-lite。

兩個實驗全部支出 < $7,主要成本是真實速度推流的 wall-clock(約 5 小時)。

## 7. 侷限與已知偏差

**共通:**

1. 噪音為單一 RIR × 單一噪音源,不同空間與人群組成未覆蓋
2. 一體式模型為 preview 版本,行為可能隨版本變動;所有原始回應已落檔
3. **Deepgram(arm D)未執行**:環境無帳號。其 keyterm prompting 上限 100 詞、
   SM 為 1000 詞且支援假名讀音標註,值得補測
4. A/G 的聽寫是 Live API 的附屬輸出(inputAudioTranscription),
   其品質不必然等於模型內部的理解

**exp1:**

5. 堺段落為 26~28 秒節錄,專名數少(6~7/段),該領域統計力較弱
6. 參考文本經雙 ASR 驗證而非人耳逐秒聽寫;驗證引擎之一與 arm C 同廠、
   另一與 arm A 同廠——但兩引擎互相制衡(採納規則要求兩引擎一致才改動頁面文字),
   正字法爭議一律以頁面為準,不偏向任一受測方
7. adequacy 面板為單一廠商(Google)三模型,非原設計的五廠
   (OpenRouter 與 OpenAI key 在本環境無效,401);評審與翻譯模型同廠可能有偏好,
   但 A 與 C/C+ 的翻譯**都**出自 Gemini,此偏差對相對比較大致抵銷
8. **C/C+ 的翻譯 hop 是對定稿逐字稿整段翻譯,A 是增量口譯**——adequacy 比較對 C/C+ 有利;
   產品化後 C 的增量翻譯 adequacy 會低於本測數字
9. manemu 原版 systemInstruction 與五廠評審面板原設定不可得,均為重寫版

**exp2:**

10. 音訊經公開鏡像取得(官方 YouTube 對資料中心 IP 擋下載);時長逐檔核對一致
11. 參考文本的英文拼寫仲裁依賴投影片與雙 Gemini 一致性,**無人耳終審**
12. 三段語料、86 個術語實例——段落層級統計力有限,
    G 在 M0 的優勢 CI 下緣壓在 0,是傾向而非定論
13. `cmn_en` 替代 `multi`:結論適用於「有專用雙語 pack」的引擎,泛多語 pack 未測
14. 譯文層 P0/P1 只在 X 系列測(G 是一體式,無法拆層)
15. exp2 未做 adequacy 盲評面板(只有召回率與 TER)

**exp5:**

16. **參考轉寫由 `gemini-3.5-flash` 產生**(gm35 預設、gm36 查一致性、SM 無投票權),
    因此 Gemini 系 arm 有主場優勢;Breeze 與 SM 之間的比較不受影響。
    見 §3E.7 的兩條反證
17. **Breeze 跑在 CPU/fp32,非 notebook 的 T4/fp16**(本環境無 GPU);
    其餘參數相同且寫進每筆 meta,但數值差異未量測
18. **SM 用 batch 非 realtime**(帳號 realtime 併發上限 1);
    方向已知——唯一同檔對照上 batch 比 realtime 低 0.057,即 batch 低估 SM
19. 3 個 segment cluster、128 個術語實例,bootstrap CI 寬;
    足以推翻「優勢可推廣」,不足以精確估計優勢大小
20. 拉丁字母分歧的 16 條裁決**沒有人耳終審**,證據是「SM 的獨立讀法 + 實體是否真實存在」
    (`exp5/corpus/reference/overrides.json` 的 `_protocol` 有記錄這條與 exp2 的差異)
21. `Gbat`/`Gbat37` 的轉寫**未做人工聽核**,LLM 是否「補出」內容未驗證
