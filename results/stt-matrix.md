# STT 選型決策矩陣

跨專案的語音辨識引擎選型參考。結論來自實測,不是規格書比較。

最後更新:2026-08-19(exp5 + exp1 追加 arm `Abat`)

---

## TL;DR

**判準有五個:要不要即時、音源多乾淨、專名多密、要不要時間戳、資料能不能出境。**

三句話版本:

1. **要即時就別碰 LLM 串流。** 一體式的「噪音崩潰」是 **Live API 的行為**,
   不是模型聽不懂——同一個檔給 `generateContent` 就好端端的(§3.1b)。
   但這不救即時場景:Live 就是即時唯一能用的介面。
2. **不要即時的話,LLM 批次現在是預設答案。** 28.8× 實時、$0.26/hr,
   乾淨與擴音失真條件下準確度全場最好。代價是**沒有 timestamp、
   沒有 diarization、不能串流**。
3. **資料不能出境就只剩地端。** Breeze ASR 25(Apache 2.0)是實測過的選項,
   抗噪夠好(§6)。
4. **錯一個詞代價高的非即時場景,兩個引擎都跑、分歧標紅給人看**(§8)。
   不要蓋 GER——天花板不在那裡,而且會多一個幻覺入口
   ([`oracle_report.md`](oracle_report.md))。

## 五個判準

### 1. 要不要即時 —— 決定你能用哪一類介面

這是產品形態問題。批次**沒有比較準**(SM 即時 vs 批次見 §3.2),但它必須等講完。

| | 可用介面 |
|---|---|
| 現場口譯、現場字幕 | 專用 ASR 串流(SM)、LLM Live API |
| 事後逐字稿、筆記、字幕生成 | 上述全部 **+ LLM `generateContent`(通常最好也最便宜)** |

**關鍵不對稱:同一家 LLM 的即時與非即時,抗噪差一個數量級。**
exp1 人聲 8dB 下 Gemini Live 召回 0.030(6 段中 4 段輸出為空),
`generateContent` 是 0.567。詳見 §3.1b。

### 2. 音源多乾淨 —— 決定要不要專用 ASR

| 音源 | 例 | 即時 | 非即時 |
|---|---|---|---|
| line-in 級 | 導覽機直插、錄影音軌、會議系統輸出 | LLM Live 可用 | **LLM 批次最好** |
| 近場麥克風 | 按住說話、桌上型會議麥 | LLM Live 可用 | LLM 批次 |
| **遠場 + 人聲背景** | 展館、餐廳、樂園、大講堂後排 | **只能專用 ASR + 詞表** | LLM 批次可用但略輸 SM+詞表 |

**分界:一旦有人聲背景(SNR < 約 15dB),LLM 的 *即時* 介面不可用。**
不是變差,是會整段放棄(§3.1)。**但它的批次介面沒有這個問題**(§3.1b)。

若要動態切換,必須以現場 SNR 偵測為依據,不能靠使用者判斷。

### 3. 專名密度 —— 決定要不要詞表

專有名詞(地名、人名、料號、術語)密集的場景,詞表對**專用 ASR** 是投報率最高的
一項投資:全條件 +0.12~0.19 召回率,一次性成本約 $0.14/單位,**延遲零代價**。

但先分辨缺的是什麼(exp2):目標詞彙是「引擎沒見過的」(在地專名、料號)
才值得做詞表;「引擎見過但語言模式不對」(中英夾雜)要先修**語言 pack**,
詞表只有 +0.03~0.05。

LLM 這條路沒有詞表機制,對應手段是 prompt 給脈絡——**本專案未量測其效果**。

### 4. 要不要時間戳 —— 決定能不能用 LLM 當 STT

字幕、對齊、逐字定位需要詞級時間戳 → **專用 ASR,沒有第二個選項**。
摘要、問答、筆記不需要 → LLM 批次直接吃音訊,更快更便宜也更準。

同理,**需要分辨誰在說話(diarization)也只能用專用 ASR**。

### 5. 資料能不能出境 —— 決定能不能用雲端

若是硬需求(法遵、廠區、醫療),雲端 API 全部出局,選項只剩:

- **Breeze ASR 25**(Apache 2.0,Whisper-large-v2 中文微調)—— 實測見 §6
- SM on-prem / Google Cloud STT On-Prem —— 本專案未測

## 應用選型指引

### 先回答三個問題

```
① 要即時嗎?
   要 ─────────► ② 有人聲背景嗎?
   不要 ───────► ④ 需要 timestamp / diarization 嗎?

② 有人聲背景嗎(SNR < 15dB)?
   有 ─────────► Speechmatics 串流 + 詞表      ← LLM Live 在這裡歸零
   沒有 ───────► Gemini Live(省一跳)或 SM 串流

④ 需要 timestamp / diarization 嗎?
   要 ─────────► Speechmatics 批次(+ 詞表)
   不要 ───────► ⑤ 資料能出境嗎?

⑤ 資料能出境嗎?
   能 ─────────► ⑥ 錯一個詞的代價高嗎?
   不能 ───────► Breeze ASR 25(地端)

⑥ 錯一個詞的代價高嗎(法遵、料號、廠區記錄)?
   高 ─────────► 並排雙跑 + 人工複核         ← 見 §8
   一般 ───────► Gemini generateContent      ← 最快、最便宜、最準
```

### 情境矩陣

| 情境 | 即時 | 音源 | 選型 | 理由 |
|---|---|---|---|---|
| **景點導覽** | 要 | 遠場吵 | **SM 即時 + 地點詞表 + Gemini 譯** | 已實測驗證(§3);kikemu 走這條 |
| **導覽機 line-in** | 要 | 乾淨 | 同上,或降級一體式省一跳 | 乾淨條件兩者打平;須 SNR 偵測把關 |
| **樂園廣播** | 要 | 極吵 + 音樂 | SM + 園區詞表 + **音訊指紋快取** | 廣播會重複,第二位使用者近乎免費 |
| **對話口譯** | 要 | 近場 | **Gemini Live 一路到底** | 語氣模仿與語用判斷拆開就沒了 |
| **餐廳短互動** | 要 | 中等 | SM 即時 + **滾動 10 秒緩衝** | 片段極短,關鍵是別錯過開頭 |
| **演講/會議逐字稿** | 不用 | 近場 | **Gemini `generateContent`** | 28.8× 實時、$0.26/hr;乾淨條件準確度全場最高 |
| **Podcast 摘要・問答** | 不用 | 乾淨 | **Gemini `generateContent`** | 不需 timestamp,LLM 直接吃音訊最省 |
| **影片字幕製作** | 不用 | — | **SM 批次 + 詞表** | 要詞級時間戳,LLM 這條路沒有 |
| **會議記錄(要分辨誰說的)** | 不用 | 近場 | **SM 批次(diarization)** | LLM 批次無 diarization |
| **影片字幕**(有字卡) | 不用 | — | **不用 STT**,多模態模型直讀影片 | 字卡是純視覺,cascaded 看不見 |
| **時間戳校正** | 不用 | — | **最便宜的詞級時間戳引擎** | forced alignment 已知答案,不需要準 |
| **法遵逐字稿・廠區**(可出境) | 不用 | 中等 | **並排雙跑:Gemini 批次 + SM 批次+詞表,分歧標紅人工複核** | 錯一個詞成本高;複核負擔約 11% 全文(§8) |
| **法遵逐字稿・廠區**(不可出境) | 不用 | 中等 | **Breeze ASR 25 地端** | 資料落地是硬需求;M3 召回 0.810(§6) |
| **中英夾雜會議(即時)** | 要 | 近場 | **SM `cmn_en` 雙語 pack** | 雙語 pack +0.23~0.29,詞表僅 +0.03~0.05(§5) |
| **中英夾雜逐字稿** | 不用 | 近場 | **Gemini `generateContent`** | exp5 M0 0.96~0.99;但參考由 Gemini 產生,有主場偏差 |

### 成本速查(每小時音訊)

| 路線 | 成本 | 速度 | timestamp |
|---|---|---|---|
| Gemini `generateContent` 3.5-flash `minimal` | **$0.26** | 28.8× 實時 | ❌ |
| Speechmatics 批次 | $0.24 | 6~12× 實時 | ✅ 詞級 |
| SM 即時 + Gemini 譯(kikemu) | $0.35 | 1×(本來就即時) | ✅ 詞級 |
| Gemini Live 一體式 | ~$0.22 + 音訊輸出 | 1× | ❌ |
| Gemini `generateContent` 3.7-flash `low` | **$2.69** | 21× 實時 | ❌ |
| Breeze ASR 25 地端 | 電費 + GPU | **T4 實測 2.9~3.2× 實時**;CPU 4 核約 0.14× | 段級 |

> **3.7-flash 不支援 `thinkingLevel: "minimal"`**(400 直接拒收),
> 只能退到 `low`,而 low 不是關閉——thoughts/output = 18.7×,成本跳 10 倍。
> **「換更新的模型」不必然更省。** 見 `docs/gemini-api-lessons.md`。
>
> 價格 $1.50/M in、$9.00/M out、gemini-3.x-flash 級,2026-08-14 核實;
> SM $0.24/hr 為官方費率。抄價前先確認是 flash 還是 flash-lite。

## 五條可以背起來的規則

1. **要不要即時是產品形態問題,不是成本問題。**
2. **「LLM 在噪音下會崩」要加上「即時」兩個字。** 崩的是 Live 串流路徑;
   同一個模型走 `generateContent` 在同一個檔上是好的(§3.1b)。
3. **有沒有畫面資訊決定要不要 STT。** 有字卡、投影片、圖表的,
   直接讓多模態模型看,不要 cascade。
4. **要 timestamp 或 diarization,LLM 這條路直接出局**,不必比準確度。
5. **看到「oracle 上限 +X」就問「選錯時的下限是多少」。** 天花板類分析
   逐項取 OR、假設你事後知道誰對;真實系統選錯時會比最佳單一引擎更差。

來源:kikemu 聽譯引擎評測(日文導覽解說,6 段 × 5 種聲學條件 × 多 arm,配對設計,bootstrap 95% CI)。

| 節 | 實驗 | 原始檔 |
|---|---|---|
| §3.1 / §3.2 / §3.3 / §3.4 / §3.5 | exp1 日文導覽 | `results/scores.json`、`results/raw/` |
| §3.1b | exp1 追加 arm `Abat` | `results/raw/Abat/` |
| §5 | exp2 中英夾雜 | `exp2/results/scores.json` |
| §6 | exp5 領域外 + Breeze | `exp5/results/scores.json`、`exp5/results/raw/` |
| 成本速查 | exp5 usage 實測 | `exp5/results/raw/Gbat*/` |

完整報告與 21 條侷限:[`results/report.md`](report.md)。

### 3.1 一體式**即時**在噪音下會崩潰,不是變差

專有名詞召回率(tolerant 判定,67 個專名):

| arm | 乾淨 | +混響 | +人群 15dB | +人群 8dB | 擴音失真 |
|---|---|---|---|---|---|
| Gemini Live 一路 | 0.836 | 0.552 | 0.194 | **0.030** | 0.582 |
| SM 無詞表 | 0.716 | 0.687 | 0.672 | 0.433 | 0.687 |
| **SM + 詞表** | **0.836** | **0.836** | **0.806** | **0.627** | **0.851** |

- **乾淨條件下一體式與 SM+詞表統計上打平**(皆 0.836)
- 差距隨噪音**單調放大**,CI 全部排除 0
- **SNR 8dB 下一體式系統性崩潰**:6 段中 4 段輸出歸零,獨立重跑逐檔重現、字元數一致。這不是抖動,是 VAD/辨識在人聲背景下整段放棄
- 譯文 adequacy:SM+詞表 4.71 > SM 4.50 > 一體式 3.61(邊聽邊譯會精簡丟細節)

### 3.1b 但那是 Live 的行為,不是模型的能力上限(exp1 追加 arm `Abat`)

同一批音檔、同一家模型,換成 `generateContent`(非串流)重跑:

| arm | N0 乾淨 | N3 人群8dB | N4 擴音 |
|---|---|---|---|
| Gemini **Live** | 0.836 | **0.030** | 0.582 |
| **Gemini 批次** | **0.940** | **0.567** | **0.896** |
| SM 即時 + 詞表 | 0.836 | **0.627** | 0.851 |

CER 說明發生了什麼:Live 在 N3 的 CER 是 **0.911**——6 段中 4 段 CER ≈ 1.0,
也就是**輸出是空的**。同一個檔給 `generateContent`,CER 0.348,
與 SM 的 0.319 同級(不是「低召回卻低 CER」那種靠猜的形狀)。

三個限定:

1. **人聲 8dB 下批次仍略輸 SM+詞表**(0.567 vs 0.627),而且 Gemini 這跳沒用詞表。
2. **乾淨與擴音失真條件下批次是全場最好**(0.940 / 0.896),贏過 SM+詞表。
3. 批次沒有 timestamp、沒有 diarization、不能串流——**它不改變即時場景的選型**。

**這一格沒有主場偏差**:exp1 的參考文本來自大阪觀光局頁面,不是任何受測引擎產生的。
(對照 exp5 的 Gemini 數字有主場偏差,見報告 §3E.7。)

### 3.2 即時 vs 批次:沒有準確度代價

| arm | 乾淨 | +混響 | +人群 15dB | +人群 8dB | 擴音 |
|---|---|---|---|---|---|
| 即時 無詞表 | 0.716 | 0.687 | 0.672 | 0.433 | 0.687 |
| 批次 無詞表 | 0.746 | 0.687 | 0.657 | 0.418 | 0.702 |
| 即時 有詞表 | 0.836 | 0.836 | 0.806 | 0.627 | 0.851 |
| 批次 有詞表 | 0.866 | 0.836 | 0.821 | 0.597 | 0.836 |

差距 −0.03 ~ +0.03,CI 全部含 0。**不必為了準確度犧牲即時性。**

### 3.3 詞表的邊際價值

| 條件 | Δ(有詞表 − 無詞表) | 95% CI | McNemar |
|---|---|---|---|
| 乾淨 | +0.119 | [+0.016, +0.211] | 8 / 0 |
| +混響 | +0.149 | [+0.056, +0.215] | 10 / 0 |
| +人群 15dB | +0.134 | [+0.037, +0.211] | 9 / 0 |
| +人群 8dB | **+0.194** | [+0.138, +0.232] | 14 / 1 |
| 擴音 | +0.164 | [+0.071, +0.234] | 11 / 0 |

- 所有條件 CI 排除 0,**愈吵價值愈大**
- McNemar 幾乎單向:詞表救回的詞幾乎沒有代價
- **對延遲與改寫率無可測影響**(partial p50 0.37 vs 0.35s;改寫率 0.16 vs 0.17)
- 邊際成本約 **$0.14/景點**(3.5-flash 真價;初版按 flash-lite 價寫成 $0.035),
  一次性,攤到每位使用者趨近於零

### 3.4 延遲

| 指標 | SM 即時 | 一體式 |
|---|---|---|
| 首字(暫定) | ~0.36s | — |
| 定稿 p50(max_delay=2.0) | ~2.3s | — |
| 首個譯文輸出 | — | ~7.6s |
| 改寫率 | ~16% | append-only |

一體式以「語意段」為單位輸出,首包 ~7.6 秒——對現場跟讀太慢。

### 3.5 自動詞表的天花板

以「地點名 + 城市名」查維基百科自動生成(每域 142~166 條),對正解專名的**字面覆蓋僅 1/6 ~ 6/7**。即便如此 C+ 仍全面領先,因為長詞條會連帶救回子字串專名。

**但在地小眾詞(小店名、舊機關名)維基百科沒有,是真實天花板。** 產品端應改用官方頁面/在地資料源,覆蓋率會顯著提高。

## 4. 已知空白

1. ~~中英夾雜(晶晶體)完全未測~~ → **已測**(exp2,李宏毅課程 3 段 × 4 條件 × 6 arm),見 §5 與 `exp2/results/report.md`

1c. **LLM 批次是否靠世界知識「猜」專名**,CER 不支持這個懷疑,但**未做人工聽核**
2. **Deepgram 未執行**(無帳號)。其 keyterm prompting 上限 100 詞、SM 為 1000 詞且支援假名讀音標註,值得補測。
3. 噪音為單一 RIR × 單一噪音源,不同空間與人群組成未覆蓋。
4. 一體式模型為 preview 版本,行為可能隨版本變動。
5. Speechmatics 即時 `multi`(melia-1)在免費帳號回 not supported;雙語結論來自專用 `cmn_en` pack,泛多語 pack 未測。

## 5. 中英夾雜實測(exp2)重點

語料:李宏毅 ML/GenAI 課程 3 段 × 5 分鐘,86 個實際講出的英文術語實例;
條件 M0 乾淨 / M1 教室殘響 / M2 辦公室 20dB / M3 會議交談 12dB。

| arm | M0 | M1 | M2 | M3 |
|---|---|---|---|---|
| SM 單語 cmn | 0.521 | 0.573 | 0.563 | 0.469 |
| **SM 雙語 cmn_en** | 0.813 | 0.812 | 0.792 | 0.563 |
| SM 雙語 + 投影片詞表 | **0.833** | **0.844** | **0.865** | **0.594** |
| Gemini Live 一體式 | 0.927 | 0.802 | 0.792 | 0.396 |

- **勝負手是語言 pack,不是詞表**:雙語 pack +0.23~0.29;投影片詞表僅 +0.03~0.05;領域通用詞表 ≈ 0
- **詞表投資判準(與 v1 合併)**:目標詞彙是「引擎沒見過的」(在地專名、料號)才值得;「引擎見過但模式不對」要先修語言模式
- 單語模式的失敗是 **F2 誤認成別的英文**(COVID-19→CoffeeNight),不是中文化;所以詞表提示救不動
- 一體式在 12dB 會議交談已半滅(0.396、TER 0.83)—— 「人聲背景斷崖」複驗成立,且比日文場景(8dB)更早
- 「詞表術語不譯」規則(P1)無增量:原版 prompt 下架構名被翻成中文的比例已是 0%
- 雙語 pack 與詞表對延遲皆零影響(partial p50 ~0.8s、final ~2.3s)

## 6. 地端選項:Breeze ASR 25(exp5)

MediaTek Research 的 Whisper-large-v2 中文微調,**Apache 2.0,可地端**。
exp5 用模型沒看過的語料(台灣科技訪談 podcast 3 段,每條件 158 個英文術語實例)量:

| arm | M0 乾淨 | M3 混響+12dB 交談 |
|---|---|---|
| Gemini 3.7-flash 批次 ※ | 0.962 | **0.880** |
| Gemini 3.5-flash 批次 ※ | **0.987** | 0.816 |
| **Breeze ASR 25** | 0.880 | 0.810 |
| Speechmatics 批次 | 0.753 | 0.646 |
| Gemini 3.1 Live | 0.930 | 0.551 |

※ 有主場偏差(exp5 的參考轉寫由 gemini-3.5-flash 產生),見報告 §3E.7。

**怎麼讀這張表:**

- **Breeze 不是「抗噪最強」。** 它在 M3 贏 SM 與 Gemini Live,但 Gemini 批次
  與它打平(3.5)或贏它(3.7,且該 arm 沒參與造參考)。
- Breeze 唯一穩坐第一的是**掉幅**:M0→M3 只掉 0.070(Gemini Live 掉 0.379)。
- **它真正不可替代的地方是「唯一能地端跑,而且抗噪夠好」。**
  另外兩家都是雲端 API,音訊一定要送出去。
- 失效模式:F1(整段漏聽)12 vs SM 的 37,但 F2(聽成別的詞)36 ≈ SM 的 37
  ——**它很少放棄,但常聽錯**。

**選它之前要知道的:**

1. **訓練資料污染是真的。** Breeze 的訓練集含 `NTUML2021`,exp2 的 S1/S2
   就是那門課。Phase A 的 Δ 是 +0.281,exp5(領域外)是 **+0.146**;
   換成 SM realtime 基準約 +0.09。**優勢被放大了約 2~3 倍。**
   評估任何開源 ASR 前,先查它的訓練資料清單。
2. Whisper 家族的老毛病(重複迴圈幻覺)仍在,見報告 §3D。
3. 沒有詞級 timestamp(只有段級),沒有 diarization,沒有詞表機制。
4. exp5 這次跑在 CPU/fp32(環境無 GPU),與 T4/fp16 的數值差異未量測。
5. **速度差很多**:T4/fp16 上 5 分鐘音檔約 102 秒(2.9× 實時,exp2 Phase A 實測);
   同樣的檔在 4 核 CPU/fp32 上要 **2089~2253 秒**(約 0.14× 實時,exp5 實測)。
   地端部署要算進 GPU 成本,不能只算電費。

## 7. 選型時的踩雷筆記

- `gemini-3.5-live-translate-preview` **會無視 systemInstruction 的目標語言指示,輸出英文**。翻譯專用 Live 模型不可控,不採用。
- Speechmatics 的 `sounds_like` 日文只吃全形假名;文件稱超過 6 字會被丟棄,實測未被拒絕但是否生效無法從 API 觀察。
- Speechmatics 註冊送 $100 額度、不需綁卡;即時約 $0.24/小時。多數評測用量落在贈送額度內。
- 詞表以 session config 送出,**中途無法更新**;要換得重連。累積到的新詞應回填到「下一位使用者」的詞表,而非本場生效。
- **不要試圖用外掛降噪救一體式即時**(exp3 實測):WebRTC NS / 譜門檻對人聲背景無效——譜門檻能讓崩潰的 Gemini Live「重新開口」,但召回率是 0(講的都不是原文);對 SM 則是零到負效果(它的抗噪是訓練內建的,不是前處理)。WebRTC NS 還會傷乾淨音源(N0 0.836→0.791)。吵雜場景的解是換引擎或改拾音物理,不是 DSP。
  (**補充**:若場景允許非即時,換成 `generateContent` 才是最有效的「解」——
  同一個模型在同一個檔上就不崩了,見 §3.1b。DSP 那條路仍然無效。)
- **看到「oracle 上限 +X」就要問「選錯時的下限是多少」。**
  oracle / 天花板類分析算的是**逐項取 OR**——每一項都當作你事後知道誰對。
  真實系統沒有那個信號,**選錯時會比最佳單一 arm 更差**,而這個下行風險
  完全不在那個數字裡。所以 oracle 是「值不值得繼續看」的篩選工具,
  不是「做了會賺多少」的估計。kikemu 的做法是:天花板夠高時,
  **把選擇權交給人(並排雙跑 + 標紅複核),不交給沒有信號可用的模型**。
  見 [`oracle_report.md`](oracle_report.md) §8b。
- **指向性麥克風的錢要花在 SM 這條線,不是一體式**(exp4 聲學模擬):Speak2 級陣列(+9dB DRR/+6dB SNR)讓 SM+詞表在 8dB 人聲下 0.597→0.791、領夾麥 0.821(貼到無噪天花板);同樣條件一體式只回到 0.284/0.507——**SM 不加任何指向性都贏 Gemini Live + 領夾麥**。會議室配 Speak2 對一體式的價值在「非尖峰時段」(M2 0.792→0.865);多人交談進行中仍不可用(0.604)。模擬取樂觀上緣,正向數字採購前需真機驗證。

## 8. 並排雙跑 + 人工複核(非即時,錯一個詞代價高的場景)

不做 GER、不做自動選擇、不讓任何模型合成新稿。**同一份音訊送兩個引擎,
token 級 diff,分歧處標紅交給人。**

- **Gemini `generateContent`** — 28.8× 實時、$0.26/hr,無時間戳
- **Speechmatics 批次 + 詞表** — 6~12× 實時、$0.24/hr,附詞級時間戳與 diarization

合計 **$0.50/hr**,約單跑的兩倍;複核人力才是主成本。

### 複核負擔實測(exp1,`analysis/dual_run.py`)

| 條件 | 逐字稿分歧比例 | 專名分歧數 | 只有 Gemini 對 | 只有 SM 對 | Gemini 佔比 |
|---|---|---|---|---|---|
| N0 乾淨 | **11.0%** | 9 | 7 | 2 | 0.78 |
| N1 殘響 | **10.9%** | 10 | 7 | 3 | 0.70 |
| N2 人群15dB | 18.0% | 11 | 6 | 5 | 0.55 |
| N3 人群8dB | **49.0%** | 20 | 9 | 11 | 0.45 |
| N4 擴音 | 11.7% | 14 | 9 | 5 | 0.64 |

1. **正常條件複核負擔約 11%**,不是整份重聽。
2. **分歧處不是一面倒**:乾淨條件 Gemini 贏 78%,但剩下 **22% 是 SM 才對的**
   ——那正是單引擎流程會靜靜漏掉的部分。愈吵愈接近五五開。
3. **N3 是這條建議的失效點**:要看的是全文一半,而勝率只有五五開。
   **人群 8dB 的解是換麥克風**(§7 的 exp4 實測:0.597 → 0.791),不是加人力。

**適用**:法遵逐字稿、廠區記錄、會議紀要——非即時、有人複核、錯一個詞成本高。
**不適用**:現場字幕(即時線天花板只有 +0.015,而且沒有人可以複核);
無人複核的自動流程(等於回到「要自動選一個」,問題原封不動)。
**前提**:音源 SNR 在 15dB 以上。

完整推導與否決 GER 的理由見 [`oracle_report.md`](oracle_report.md)。
